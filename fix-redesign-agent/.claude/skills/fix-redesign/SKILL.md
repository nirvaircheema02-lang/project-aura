# fix-redesign — targeted page fixes and design review resolution

Read the project's `AGENTS.md` and `docs/REDESIGN_RULES.md` first (paths relative to
the fix-redesign-agent root). They apply to CLI outputs, generated React previews and hand-authored preview overrides.
For selected findings with `NEEDS_REVIEW`, `UNVERIFIED`, no compatible DS match or
no exact design prescription, load [Design Review Resolver](references/design-review-resolution.md)
before deciding what to build. In a run, the same decisions are produced by the **RV node** (see Steps):
you answer its judgment bundle, and everything you claim is re-verified in code. Suggestion-only requests
remain read-only: do not launch a fix run or write artifacts.

**Read this whole file before doing anything.** This skill exists so "redesign the page from that run" never turns into an architecture discussion. If you find yourself about to change a node contract, the output layout, a gate, or the PASS/PARTIAL/FAIL rule to make a run "work", stop — that is out of scope here; note it for the user instead. Full spec: `docs/ARCHITECTURE.md`.

## What you take from the user

**The startup input is `Run ID` (or `Run Name`) + `Mode` (Full Page | Selected Sections) — nothing else.**
Resolve the matching audit run, its `data.json` (audited URL, findings, evidence), `fix-plan.json`
and the Design System yourself (`redesign --run-id <id> --dry-run` does it); never ask for files that
are already present, and never ask for a save path. A project name, an existing redesign run id, a run
folder, a dashboard URL or a Fix JSON path also identify the run. Check the Fix JSON's runId against the
audit run as well as joining findingIds; matching IDs alone do not resolve a runId mismatch. Report
conflicts; never silently rewrite audit inputs (change one only on the user's explicit instruction, with a
backup). Ask for the mode only if the user did not give it — the CLI refuses a real run without `--mode`.

## What every run delivers — the React Preview (default, every page, every mode)

- **The default deliverable is a running React preview: runnable React source (`<run>/preview-app/`) and a
  localhost URL.** It is GENERATED by the pipeline (node R8) from the run's own captured evidence and
  verified before G2. Do not hand-build a preview per run, and never present the static HTML export
  (`redesign.html`, `redesign-content.html`) as the preview — it is a reference snapshot only. There is no
  silent fallback: if R8 cannot generate, build, serve or measure the preview the run FAILS there; report
  that, never substitute static HTML.
- **Selected Sections:** only sections that contain a finding marked `fix` (scope = `context/scope.json`),
  each rendered **complete**, in original order, original content and composition preserved, verified DS
  fixes applied. Unselected sections and the global header/footer are **absent** (not hidden, not marked).
- **Full Page:** every page-specific section; the global header and footer stay excluded.
- **Verify before G2** (R8 does it; you report it): scope, content preservation, each Fix finding and each
  **resolved target measured in the rendered preview, in its own state** (an element merely existing proves
  nothing), **design/state fidelity** against the immutable baseline of the original (default, hover, keyboard
  focus, columns/grouping/order, alignment, sticky pin/release; only a target-authorized change may differ),
  interaction parity with the original page (B1 captured the original's behaviour read-only before any edit),
  runtime hygiene. Whatever could not be compared is reported NOT checked, never passed.
  Anything simulated (forms do not submit) or not reproduced (JS-driven widgets the generator cannot derive)
  is listed in `redesign/PREVIEW.md` and at G2 — surface it before asking for visual approval.
- Closing a not-reproduced gap for a page is a **hand-authored override**, not a new preview: write a React
  module under `<run>/preview-overrides/`, register it in `<run>/context/design-decisions.json`
  (`overrides`, plus per-finding `findings` resolutions from the Design Review Resolver), optional
  `preview-overrides/checks.mjs` for its behavioural checks, then
  `pnpm run agent preview <redesignRunId> --regenerate`. Overrides are labelled hand-authored in the
  verification. Never set a finding to `preserve-existing` just to turn it green.
- A proposed local component composition/variant does not activate the L-series, authorize a shared-DS
  edit or authorize publication. **Component creation and publishing are out of scope.**

## Steps

1. **Dry run first, always:**
   `pnpm run agent redesign --run-id <id> --dry-run` (or `--run-name "<name>"`). This runs R1 for real: resolves the run via audit-agent's `find-run`, validates `data.json` + `fix-plan.json` (+ `new-component-plan.json` when present), loads the Design System registry, and prints the findings marked Fix. It writes nothing and needs no model credential.
   - If audit-agent reports **zero or multiple** matches, show its candidate list and ask the user to pick or give the exact Run ID. Never guess.
   - If the run **has no `fix-plan.json`**, decisions have not been imported — report it; do not fabricate them.
   - Report actual node availability, distinguishing implemented code from enabled CLI routes.
2. Show the source run, scope, Fix counts and unresolved design decisions. Existing
   authorization to fix the selected findings covers routine DS design choices; do not
   ask the user to choose every token or approve each review item. For unclear behavior
   or a necessary change outside scope, show the concrete proposal and ask only for the
   missing decision. Honor actual CLI review gates.
3. Run `pnpm run agent redesign --run-id <id> --mode full-page` (or `selected-sections`).
   - **Judgment provider defaults to `claude-session`: no `ANTHROPIC_API_KEY`, no separate API billing.** C2/R3/R5's judgment is performed by YOU — the Session Agent running this skill — not by an external model call. `judgmentProvider: "anthropic-api"` in config is the only way to go back to a direct API call, and only that mode needs the credential.
   - Node order: R1 → R2 capture → C2 map → scope/G1 → **B1** (read-only capture of the original's behaviour and the immutable design/state baseline) → **RV resolve targets** → [R3 plan → R4 apply → R5 compare]×≤3 → R6 manifest → R7 static export → **R8 React preview (generate · build · serve · verify · bounded correction loop)** → (planner re-plans of what only the planner can fix, within the same budget) → **G2**.
4. **Every run stops at one of TWO distinct kinds of pause — tell them apart, never conflate them:**
   - **A judgment pause** (claude-session mode, C2/R3/R5): the command prints "Awaiting judgment" plus a node, a bundle id, and the run folder. This is not a human gate and needs no user decision — it needs YOU to perform that node's judgment. See "Processing judgment bundles" below. Keep processing bundles, one `judgment submit` at a time, without going back to the user, until the run reaches an actual human gate or completes — a single "redesign this page" instruction should carry the run all the way to the next gate or to completion, not stop and ask permission per bundle.
   - **A human gate** (`G0`–`G2`): the command's output says exactly which gate, why, the run folder, and the `review/review-index.html` path — that page links every export, preview and validation result the gate's decision is based on. **G2's reason line carries the React preview URL and its verification verdict**; relay the URL, the source path (`preview-app/`), the verification summary, the failed checks, and the "not reproduced" / "simulated" lists from `redesign/PREVIEW.md` — do not summarize the HTML from memory. G0/G1/G2 decisions are the user's to give in chat; you record them with:
     `pnpm run agent decide <redesignRunId> --gate <G> --outcome <outcome> [--note "<text>"]`
     then `pnpm run agent resume <redesignRunId>`. **Never record a G2 decision yourself and never approve G2 on the user's behalf; ask.** `decide G2 --outcome approve` is refused while the preview's verification has failed checks unless the user explicitly accepts them (`--accept-preview-failures`, recorded in the note). G1 may be resolved silently only when nothing in scope is ambiguous (e.g. an excluded global section without Fix findings), with the reason in `--note`.
   - **What the new stages tell you.** `context/resolved-targets.json` lists, per finding and property, whether it is a resolved target, preserved, or unresolved (and why); `preview/fidelity.json` is the comparison with the original; `preview/correction-log.json` is what the loop did and what stayed open. G2's reason line reports fidelity, unresolved targets and any required check that is NOT satisfied — relay these, and never describe a finding as fixed while `required.open` is non-empty.
   - **Verified / failed / unverified are three different things.** A fidelity verdict of `incomplete` means nothing regressed but a REQUIRED check could not be verified (the report lists which and why: an uncaptured state, a capped or budget-stopped section, a hand-authored override, a baseline from an older version…). Relay the numbers and the first gap; never call it a pass, and say plainly when G2 approval would accept unverified checks (the decision note records them). A preserve decision is "preserved" only when `preserved-verified`; `unverified` preserves are open required checks, `failed` ones are defects.
   - **The preview's overall status is PASS, FAIL or INCOMPLETE** (same headline in `verification.json`, the preview bar, PREVIEW.md, the CLI and G2): PASS only when every required check is verified; INCOMPLETE means required evidence is missing (relay the listed gaps); FAIL means a required check failed. Disclosed limitations are separate and never change it. Report the status verbatim; never call an INCOMPLETE preview verified. `decide G2 approve` on FAIL needs `--accept-preview-failures`; on INCOMPLETE the note records the accepted unverified requirements — still the user's decision.
   - **One persisted correction budget** (`context/correction-state.json`: 2 cycles, 3 verifications, 15 minutes of active time) is shared by resume, judgment continuations, planner re-plans and `preview --regenerate`. When it is exhausted the run does no new verification, keeps the valid previous evidence and reports INCOMPLETE with "verification budget exhausted". Only an explicit `resume|preview --regenerate <id> --reset-budget` restarts it (ask the user first; it is recorded); a damaged state file blocks resume until restored or reset.
   - **A preview failure reopens a finding the live page measured fixed.** R8's feedback goes to R3 as structured items (finding, target and part, property, state, viewport, expected, observed); the re-plan is limited to those properties/states, keeps earlier successful edits, and is re-verified inside the same budget. Items no targeted edit can represent (mobile-viewport, preserve-broken) are reported, not planned. In claude-session mode, when R3 is re-asked it shows the feedback beside the finding: answer only what it names and say honestly when the cause is not the plan (the preview generator or the cascade).
5. Report the CLI's own summary **verbatim**: run outcome (`completed` / `blocked` / `awaiting-judgment` / `awaiting-approval` / `failed` — never upgraded, and never conflated with the separate page verdict PASS/PARTIAL/FAIL), iteration count, the redesign run folder, the preview URL and verification summary, and for anything but a clean PASS the exact failed checks. State that audit-agent's `data.json` / `fix-plan.json` / `new-component-plan.json` were read only (their sha256 is in `run.json`).
   - Account for **every** Fix finding from `redesign/finding-accounting.md`: fixed (measured) / DS component (measured) / unresolved / not in the preview — with reasons. Never report a finding fixed that the accounting does not.

## Processing judgment bundles (claude-session mode — C2, RV, R3, R5, L2, L3)

C2/RV/R3/R5 are relevant to the currently enabled page route. **RV** asks only the residual design
questions (selected NEEDS_REVIEW/UNVERIFIED findings): answer them with the Design Review Resolver workflow,
naming an approved reference only when the bundle lists it. The pipeline re-verifies every claim (tokens
must exist in the DS, values must be built from tokens, composition properties are refused, references must
be approved and verified) and records a rejected claim as unresolved with its reason — so answer
conservatively and say plainly what the evidence cannot settle. Never fabricate a mapping, audit mismatch
or successful verdict. A reference's colour is never written down as a raw value: the pipeline maps it to an exact or nearest suitable DS token (see the reference below) and refuses the pattern when nothing suitable exists; never claim a "proposed local variant" built from a raw colour. L2/L3 references below describe preserved component workflow behavior, not
permission to enable or execute it.

When the run stops "Awaiting judgment", the pipeline has written a versioned bundle to `<runDir>/judgments/<bundleId>.bundle.json` and is waiting for YOU to play that node's role — not the user, and not an external model call. Loop this until `resume`/`submit` lands on a real gate or completion, all within the current instruction:

1. `pnpm run agent judgment show <redesignRunId>` — auto-selects the one pending bundle, or lists them if several are pending (pass the id explicitly then). Prints the node, its instructions, its prompt, every referenced image **path**, and the exact JSON Schema your answer must satisfy.
2. **For R5 and L3, actually open the referenced screenshots (Read tool) before answering** — the bundle gives you real paths, never re-embedded bytes, specifically so you can inspect them yourself. Judge each node exactly as its role is specified in `docs/ARCHITECTURE.md` §3.2/§6.4/§9.4: C2 proposes among already-objectively-passing candidates only; R3 plans targeted DOM edits from the DS catalog/tokens/rules; R5 compares before/after and flags regressions; L2 writes component code within its declared write set; L3 judges a rendered component against its reference.
   - **If you genuinely cannot inspect an image** (none is referenced, or the file is unreadable) — never guess or fabricate a visual verdict. Keep every deterministic part of your answer (the parts objective checks/measurements already cover), set the vision-facing field to `NOT_CHECKED` (R5's `vision`; L3's `visionVerdict`), and do not report a full PASS on the strength of an uninspected image.
3. Write your answer as a JSON file matching the printed schema exactly (field names, enum values, nothing extra). On R3 iterations ≥ 2 you are re-planning only the findings still open; edits applied earlier stay on the page and count toward R5, so do not repeat them — list a finding as `unaddressed` with the specific recorded conflict (e.g. a rule that forbids the audit's target) rather than inventing an edit.
4. `pnpm run agent judgment submit <redesignRunId> --file <path-to-your-answer.json>` — validates it against the node's real schema (not just the loose JSON Schema shape) and, only if it passes, resumes the pipeline automatically. An invalid submission is refused with the exact validation issues; fix your answer and submit again — it does not consume a retry against the node's own retry budget (§7.5), since no submission was ever accepted.
5. The resumed run either reaches another judgment bundle (repeat from step 1), a human gate (go to step 4 of the main flow), or completes. Never stop and ask the user "should I keep going" between bundles — that is exactly the loop this mode exists to avoid.

**Never**, in claude-session mode: spawn a nested `claude` process, read or reuse Claude Code's own credentials/session tokens to call an API yourself, or silently fall back to `anthropic-api` because a judgment felt hard. If a bundle's request is genuinely unanswerable (e.g. the schema asks for something the given evidence cannot support), say so in the submitted judgment's own free-text fields (a low confidence, an honest "unaddressed"/`NOT_CHECKED`) rather than inventing certainty — the same standard §6.4/§8.9 already hold an external model call to.

## Hard rules

- Never write into audit-agent's tree, database, or Figma outputs. Never copy its run files here.
- Never touch the target website's source repo or hosting — capture is read-only navigation; edits happen in an ephemeral browser context. Component work happens on a **local** Design System branch only.
- Never push, commit-and-forget, or open a PR against the Design System repo without an explicit push approval (G4 "approve & push" or G5) recorded via `decide` — a local commit is not the same thing as a push, and neither implies merge or deploy.
- Never report `PARTIAL`, `FAIL`, `blocked`, `awaiting-judgment`, or `awaiting-approval` as done. Never silently drop a finding or a component — R1 reports unknown ids, R3 lists `unaddressed` findings, L1 lists `ambiguous`/`blocked` components.
- Output location is automatic (`projects/<project>/redesigns/<sourceRunId>-<runType>-<stamp>/`) — never ask for a save path.
- The React preview is the deliverable. Never substitute or present static HTML for it, never hand-build a per-run preview outside `preview-overrides/`, and never claim a finding fixed, a section complete or an interaction working unless `preview/verification.json` / `finding-accounting.md` say so. Report `not reproduced` and `unresolved` items to the user instead of hiding them.
- Production access is read-only navigation: B1/R2 never click links or submit controls, never submit a form, abort every non-GET request and analytics call. Do not copy credentials or tokens that appear in a site's public bundles; note them for the user instead.
- G2 (visual approval) is the user's decision. Do not record it yourself.
- Component creation, shared-DS edits and publishing remain out of scope.
- In claude-session mode, never spawn a nested `claude` process and never extract/reuse Claude Code's own credentials to make an API call yourself — you (the running Session Agent) ARE the judgment, performed in-conversation, recorded to a file, nothing more.
