# Audit Agent — Operating Workflow

**Companion to:** [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) (the system's structure — nodes, edges, contracts, skills). This document is the runbook: how to invoke and operate the Audit Agent, not what it's made of.

## Entry points
- `/audit-site <url>` — full-site mode
- `/audit-page <url>` — single-page mode

Per `ARCHITECTURE.md` §0: `mode` is explicit and is the sole routing source of truth — never inferred from URL shape.

## Full-site sequence
1. Provide `url` (site root) + `mode=full-site`.
2. A1 Site Mapper discovers/canonicalizes URLs → `site-map.json`.
3. A2 Template Classifier groups pages into template families.
4. **Scope Confirmation Gate** — reviewer sees estimated page/template count + B-instance count, approves or adjusts scope before dispatch. Skippable for trusted re-audits.
5. A3 Audit Dispatcher fans out parallel B instances (bounded concurrency, own `BrowserContext` each).
6. Each B instance runs the Page Audit sequence (below).
7. A4 Site Consolidator merges results, dedupes, finds root causes, builds the Master Result.
8. **Publish Confirmation Gate** — reviewer sees the Master Result before C3 writes to Figma.
9. C3 publishes to Figma, C1 writes the Excel report, and C4 serves the run at its local dashboard URL — **all three mandatory**. C2 persists JSON (internal backing data; also what C4 reads).

## Single-page sequence
1. Provide `url` (exact page) + `mode=single-page`. The URL is canonicalized first (`ARCHITECTURE.md` §0).
2. B1–B7 run directly — A1–A4 are never invoked, regardless of `url`.
3. If a previous baseline exists for this URL, diff into NEW ISSUE / STILL OPEN / RESOLVED / REGRESSION.
4. **Publish Confirmation Gate** — same gate as full-site, keyed to "before C3," never to A4 (A4 doesn't run on this path).
5. C3 publishes to Figma, C1 writes the Excel report, and C4 serves the run at its local dashboard URL — **all three mandatory**. C2 persists JSON (internal backing data; also what C4 reads).

## Page Audit sequence (B1–B7, shared by both modes)
B1 Page Analyzer → B2 Component Detector → B3 DS Matcher → conditional:
- match found, confidence ≥ MEDIUM → B4 Compliance Auditor → B5 Visual Verifier
- no match, or confidence LOW → B6 New Component Evaluator

…and always last, for every page: **B7 Final Audit Coverage & QA** — an independent check that every meaningful item on the rendered page was audited, excluded with a reason, flagged for review or reported as a capture failure (see "Final coverage — B7" below).

Low-confidence outputs at B3/B5/B6 route to the Escalation Queue instead of publishing directly.

In the implementation these branches are a data partition, not graph branches: B3 splits a page's components into *matched* (an existing DS family represents them) and *unmatched* (none does); B4 processes the matched set and B6 the unmatched set, and B5's completeness pass routes whatever it recovers or flags the same way (see the coverage guarantees below).

**Matching a measured value to the Design System (permanent rule, B3/B4).** Which DS value a measured number should become is always resolved in this order, stopping at the first step that answers: (1) the **exact value of the matched component variant** — a nearest-token search never overrides it; otherwise (2) the **single nearest valid token of the property's own token family** (type size, spacing, radius… — e.g. `6px` radius → `5px`, `32px` heading → `31.25px`), after rem/em/px are normalised to one unit; otherwise (3) **Not resolved / `UNVERIFIED` / `NEEDS_REVIEW`** with the reason — never a guess. Tokens of unrelated families are never compared, and the element's semantic identity (tag, role, component family) is decided separately and never changed by a visual/token match (an h2 that is visually nearest "level 3" stays an h2). The same B3/B4 code runs for single-page, full-site and re-audit runs; there is no per-page or per-property special case. Full rule: `.claude/skills/audit-run/SKILL.md` → "Nearest-match precedence"; decision #38 in `docs/ARCHITECTURE.md`.

**What a page audit guarantees to reach (permanent rule, B1/B2/B3/B4/B5/B6).** Every audit candidate is either audited, excluded with a reason, or explicitly unresolved in the report — there is no silent drop — and each stage owns one part of that, none re-doing another's:
- **B1** assigns elements to sections by the section's y-range **and** its own DOM subtree: a sticky scroll stage or clipped panel that renders content beyond its box keeps it, and the section's note says so. A B1 capture gap is fixed in B1, never by widening B2.
- **B2** finds and classifies the candidates — including **non-interactive status badges** (a bordered/filled text leaf) and, when B5 asks, a repeated card-scale block that has a visible surface (a card; a bare one is a layout column, excluded with its reason) — and samples a repeated group only when it is a real listing (≥ 12 members, or a B1-flagged listing: the first 5 are audited, the rest are counted in the report as "N of M"). A smaller repeated group, such as a multi-row feature grid, is audited in full.
- **B3** decides which Design System **family** an element IS before it scores how well it is styled: the DS rule names the family for the type, the rule's own files are searched first, then the rest of the family (Badge/Tag/Chip/Pill/Label/Status; the other R4.4 cards), and B3 records what it searched. A badge or card detected from its structure alone (LOW confidence, no role) may claim its family. **Existing DS family + wrong styling ≠ New Component.**
- **B4** audits a matched element against **that component's full contract** (radius, border, background/colour, typography, padding/gap, size, shadow/effect, state) plus the foundation rules under the precedence above: a `6px` radius → the Badge variant's own `5px`, and **decorative colour compliance** (brand red on a non-CTA border or fill is forbidden decoration, R1.2 — a prohibition that stands next to the variant's mismatches).
- **B6** is for a pattern **no existing DS family** represents — never an existing component implemented wrongly, never an element merely because B5 recovered it. `Recovered ≠ New Component`.
- **B5** is the final verification/completeness stage. **Every element it recovers or re-routes takes the same path a first-pass one takes**: B2 classifies it → B3 searches the family → B4 (a family exists) or B6 (none does) → B5 verifies. Per pass it checks **element coverage** (→ B2), **DS-matching coverage** (→ B3: B3's recorded family search is verified; a missing or wrong one is re-asked and the element re-routed) and **property coverage** (→ B4: foundation rules and the matched variant's full contract are recomputed and a gap rebuilt) — at most **2 passes**, **2 attempts per item**, and whatever is still unresolved is marked **NEEDS_REVIEW**, never dropped and never looped. It distinguishes a **valid exclusion** (a plain caption, label or stat; a layout column; an off-domain link; a listing member sampled out on purpose — informational, never an error) from a **capture failure** and a **genuinely unresolved reference**; only those last two count as errors (`coverage.droppedRefs`, the reports' "unresolvable element" counts), and each also becomes a NEEDS_REVIEW finding.

No new agent, node or graph edge was added for these guarantees: the graph is `B1 → B2 → B3 → B4 → B5 → B6`, followed by B7 (below) (B5 calls the other stages' own functions in-process for what it recovers; the B6 node never sees an element twice), the same code for single-page, full-site and re-audit runs. Full rule: `.claude/skills/audit-run/SKILL.md` → "Coverage: section ownership, sampling, family search and B5 verification"; decisions #40 and #41 in `docs/ARCHITECTURE.md`.

**Heading roles, and Design System first / approved Project Aura reference second (permanent rule, B2/B3/B6, engine r4–r5).** The role of a heading-like text is decided from the section's whole text hierarchy **before** any Design System component is chosen — an `h2`/`h3` tag never decides identity: a small upper-case `h2` such as `ABOUT KEN SURVEY` is an **eyebrow / supporting heading** (Ken red on a light surface, the DS inverse treatment on a dark one — never forced red), the visually dominant text is the **main section heading even when it is a `<p>`**, and the text beside it is **description / supporting copy**; the nearest-size match to a `SectionHeading` level happens only after the role is right. The matching priority is fixed: **(1) exact DS component / pattern → (2) closest valid DS family / variant → (3) approved Project Aura reference pattern (`reference/approved-reference-patterns.json` — Report Store, Case Study, Competition Benchmarking; supporting evidence only, consulted only when the DS search was undecided, never a replacement for the DS) → (4) `NEEDS_REVIEW` → (5) B6 only for a genuine no-family / no-pattern.** A pattern consistent across the approved pages but absent from the DS is surfaced as a *reference-backed* Design System candidate for governance; a divergent or single-source one is `NEEDS_REVIEW` with the pages' own values listed. Full rules: `.claude/skills/audit-run/SKILL.md` → "Heading role before nearest-size matching" and "Design System first, approved Project Aura reference second"; decisions #44 and #46 in `docs/ARCHITECTURE.md`.

**Final coverage — B7, a recovery LOOP (permanent rule, engine r5; loop r7).** After every page's B1–B6, B7 builds **its own Coverage Manifest of the rendered page** — DOM, accessibility tree, visible text, computed style, geometry, interaction state; never B2's candidate list alone — and gives every discovered item exactly one state: `AUDITED` (a `MATCH` is an audited result — never unaccounted), `EXCLUDED_WITH_REASON`, `NEEDS_REVIEW` or `CAPTURE_FAILED`. **B7 does not stop at reporting what is unaccounted.** While anything is, exactly those items go back through the stage that owns each of them: a missing element → B2 → B3 → B4 / B6 · a wrong semantic / text role → B2/B3 · a missing DS match → B3 · a missed property or compliance check → B4 · no existing DS family → B6 · content only an interaction reveals (hover layer, tab, accordion, dropdown, carousel slide) → a reveal — once per hidden layer, every member captured while it is open — then the normal flow. They are re-audited with the same B2/B3/B4/B6 logic as the first audit (no duplicate finding; an audited element whose DOM stamp the page erased is still accounted for), the **manifest is rebuilt and reconciled after every round**, and B7 runs again: `B7 → recover → re-audit → B7 → recover → re-audit` until **`unaccounted = 0`**. It always converges: an item gets two attempts and is then settled into an explicit, reasoned state (`EXCLUDED_WITH_REASON` — intentionally non-auditable · `CAPTURE_FAILED` — technically impossible to capture · `NEEDS_REVIEW` — unresolved, recorded in the Coverage ledger); a round that changes nothing, twice, ends the loop; count / time / capture limits stop a pathological page, and only an item B7 never got to examine because of that limit stays unaccounted. The user never has to ask for the recheck — the CLI prints `Coverage: RECHECKING · N discovered · R remaining` while it runs. B7 also re-derives every text item's role from the whole section hierarchy and catches a role the audit got wrong (`ABOUT KEN SURVEY` audited as `SectionHeading`; a main heading implemented as a `<p>`; stat text ignored). The final output is the **Coverage Gate**: `discovered · audited · excluded with reason · needs review · capture failed · unaccounted` — it **passes only when `unaccounted = 0`**; otherwise the audit is **INCOMPLETE**, the CLI exits with code 3 and the report names exactly what is missing. The HTML Summary carries it as ONE compact line (`Coverage: PASSED · 473 discovered · 473 accounted · 0 unaccounted`) with the whole ledger in a collapsed `Coverage details` accordion. This is 100% accounting, not a claim of 100% correctness. It is the same code for single-page, full-site and re-audit runs; a full-site run reuses a page only if its previous ledger exists and its gate passed. Full rule: `.claude/skills/audit-run/SKILL.md` → "B7 — Final Audit Coverage & QA"; decisions #45 and #47 in `docs/ARCHITECTURE.md`.
**Recovered-item section ownership & one finding per element (permanent rule, engine r8; every mode, every run kind).** Everything B7 recovers or reveals keeps its TRUE owning section, decided from the page's structure — the section the audit already holds it in, B1's adoption by DOM ancestry, the B1 section root whose DOM subtree holds it, the owner of the control that reveals it, its Header / Footer region — and geometry only for an item in the normal flow; the owner is revalidated from the live element before the finding is written. A header mega-menu, dropdown or footer drawer therefore stays under Header / Navigation / Footer even while it overlays the hero; carousel and tab content stays in its parent section; an overlay nothing in the structure owns is listed under `(outside any section)` with a review note, never under the nearest visible section. And one physical element yields ONE finding: element identity is canonical DOM path + DOM role + normalised words + section, a recovered finding is reconciled against the findings the audit already holds (same finding id kept, evidence merged, strongest valid classification preserved), and a final dedupe validation runs before the report is generated — while the same words in different sections and genuinely different DOM nodes in a repeated list remain separate findings. (Decision Log #48; `src/agents/b7-coverage-qa/ownership.ts`, `identity.ts`.)
**Global chrome first — Global Header / Page Content / Global Footer (permanent rule, engine r9; every mode, every run kind).** B7 resolves every item to a structural region before any page section is consulted. Everything inside the page's own banner (`<header>` / `role=banner`) — its base navigation, every menu and mega-menu, search, the account / user menu — and every overlay opened from it, even one rendered outside the header's DOM, is the **Global Header's**, grouped as Base Navigation · `<Label> Menu` (named by the control that opens it) · Search · Account/User Menu; a footer drawer is the **Global Footer's**; the hero owns ONLY what sits in the page-content hero's own subtree, and a hero carousel / a section accordion keep their own section. Geometry is a fallback for normal-flow content only — never for a header menu over the hero — and a detached overlay no structure owns is `(outside any section)` with a review note, never guessed into the hero. The HTML report groups accordingly (Global Header with its sub-groups, then the hero and the page's sections, then Global Footer), and the Global Header and Global Footer are **accordions — collapsed by default, a disclosure `<button aria-expanded>` each, opened automatically by a filter or search that targets their findings; the hero and every normal section stay as they are** (`html-report-v18`, report-layer only; each accordion row's chevron sits at its far right — right when collapsed, down when expanded). No new agent: this is B7's ownership and grouping, the same for single-page, full-site and re-audit runs; in a full-site audit `location.region` is the same key on every page, so header findings are never attributed to a page's hero. (Decision Log #49; `src/agents/b7-coverage-qa/ownership.ts`, `regions.ts`.)
**Findings section spacing (locked template rule, introduced in `html-report-v17`; every report, every mode, every project).** In the Findings view each new section starts a little apart from the one above it: **10px before each new section header** — never between individual finding rows, never before a sub-group header, never before the first section — with **10px of vertical padding in a section header** (sub-group headers keep 8px); the Global Header / Global Footer accordion buttons are drawn the same. It is one shared template, so the standalone report and the live dashboard inherit it for every future audit with nothing to remember or request; it changes only by an explicit template change (version bump + the pinning test).
**Role-first typography (permanent rule, engine r10; every mode, every run kind).** The order is fixed: identify the element's ROLE (from the section — never the tag or the size alone), select the DS rule or component the role names, then compare its typography. R1.3's valid sizes are the DS's own: the Major Third steps (12.8 / 16 / 20 / 25 / 31.25 / 39 / 48.8 / 61 / 76.3) plus the exceptions R1.3 documents (14 · 14 · 11 · 10); legacy remap tokens (`--text-md` 18, `--text-13/24/30/32`), component tokens (`--button-font-*`, `--badge-*-font`) and aliases never make a size valid for general text, and 12px is not a DS size. A **card title** (a title over a smaller description, repeated across the section's cards) is judged by the card-title contract (R4.3.5: 20px with 4+ cards, 25px with 2–3; DM Sans 500); a short heading-tagged **label** below the DS heading range is audited on the foundation rules like body text and is never forced into SectionHeading. A clean text element reports **foundation checks passed — not a component match** (`comparison.basis`), and its property table shows each verified property as verified. (Decision Log #51.) **FAQ questions** (a clickable heading phrased as a question, below the DS heading range) are judged by the DS AccordionItem question (`--text-sm` 16px, 500; the documented 14px compact-text exception is accepted too) — the nearest DS match, never SectionHeading's 31.25px — and a short **clickable** heading below that range is a label (engine r11, Decision Log #52).





**Full-site reuse follows the audit engine (permanent rule).** A full-site run reuses a page's previous findings only when its DOM, the Design System **and the audit engine** are unchanged. `policy_version` carries the engine's behaviour revision (`AUDIT_ENGINE_REVISION`, `src/graph/run-metadata.ts`), so after any change to what B1–B7 detect, match, compare, account for or report, a page audited by the older engine is audited again instead of keeping its stale findings; with nothing changed, reuse still works. A guard test (`test/unit/engine-revision.test.ts`) fails until an engine-source edit is acknowledged with a revision bump or a re-pin. Full rule: `.claude/skills/audit-run/SKILL.md` → "Engine revision & full-site reuse"; decision #39 in `docs/ARCHITECTURE.md`.

## Gates — what a human actually does

| Gate | When | Reviewer sees | Decision |
|---|---|---|---|
| Scope Confirmation | full-site only, before A3 dispatch | template families, page count, estimated B-instance count | approve / adjust scope |
| Publish Confirmation | both modes, before C3 | the Master Result (full-site) or Current Page Result/re-audit delta (single-page) | approve / hold |
| Failure Threshold | full-site only, if batch failure rate crosses threshold | trial-batch result after automatic half-open retry | approve continued run / abort |

All three time out to a fallback reviewer — never auto-approve, never auto-reject.

## Escalation Queue review
Findings with `reason: LOW_CONFIDENCE` or `reason: NODE_FAILURE` sit in `escalation_queue[]` until reviewed; a `RESOLVED` outcome feeds back into the run's finding set.

Expect to see placeholder-looking dynamic values here too (e.g. a stat counter still reading "0+" after settling) — per `ARCHITECTURE.md` §2.7 the agent can't tell a genuine site bug from an animation it couldn't trigger, so it escalates rather than guessing. That judgment call is yours.

## Re-audit
Providing a `url` with an existing baseline (either mode) triggers the diff sequence against the prior stored result (audit-state history) instead of a fresh first-time audit. The nearest-match precedence above applies to a re-audit exactly as to a first audit; when it moves a recommendation to a nearer valid value or variant, the finding shows it as a baseline change ("compared against X this run, Y in run Z", `ARCHITECTURE.md` decision #29) — never as a regression or a resolution. The same holds when the audit **engine** changed since the baseline (the engine revision in `policy_version`, decision #39): the page is audited again by the current engine and the difference is reported as a baseline change, not as a regression or a resolution.

## Projects and runs
Every audit target is a **project** under `projects/<project-name>/`, created on first audit. Every execution or re-audit of that target is a **run** inside it (`projects/<project-name>/runs/<run_id>/`). A project's `project.json` persists its Figma destination (file key/URL) so every run — including future re-audits — updates the *same* Figma file automatically, instead of creating a new one each time.

## Report formatting (permanent rule)
Every report shows an **Expected typography value in `rem` with its resolved px beside it — `2.441rem (39.06px)`** — in the Expected-value summaries, the property comparison / detail tables and the recommendation / detail views, on every surface (HTML report and dashboard, Figma plan, Excel). It is display formatting only: the DS token/value, `data.json`, the finding's expected value, its status, matching, nearest-match and recommendation text are never changed; the report layers draw the string through one shared module (`src/output/display-values.ts`) using the audit's own rem → px conversion at the page's **measured** root font size (`pageSummary[].rootFontSizePx`, recorded at capture — the 16px browser default applies only to a run that recorded none), nothing hardcoded. It is part of both locked templates, so it moved them to `html-report-v11` / `figma-layout-v5` (the Coverage Gate later moved them to `html-report-v12` / `figma-layout-v6`, and its compact HTML presentation to `html-report-v13`; the rule is unchanged). Typography means `font-size`, `line-height`, `letter-spacing`, `word-spacing`, `text-indent`; every other value (a token, `em`, a spacing or radius `rem`) is shown as before. Full rule and its tests: `.claude/skills/audit-run/SKILL.md` → "Report formatting rule"; decision #42 in `docs/ARCHITECTURE.md`.

## Where results land

> **v1 status correction (Decision Log #31/#32) — supersedes the "three mandatory outputs" claim below.**
> Figma is **not** automatic today, and is not gated the way this section originally described. What's actually automatic, from `pnpm run agent audit-page`/`audit-site` alone, with no further steps: **C2 JSON, Excel, the standalone HTML report, and the local Dashboard.** These four are written by the CLI itself, in no-api mode by default, for every run.
> Figma is different because Figma's MCP write access requires a live, authenticated interactive session — a plain CLI process cannot drive it (a headless Claude Code publish is a documented, still-unresolved auth blocker, IMPLEMENTATION-PLAN.md §6). So every run **does** automatically compute and persist `figma-plan.json` (the full page/marker content, `PublishPlan.markerGroups`/`globalComponents` included, `src/figma/publish-plan.ts`) and `figma-composite-plan.json` (the full-page tile geometry, `src/figma/page-composite-plan.ts`) — everything a publish needs — but nothing actually writes to Figma without a Claude Code session with Figma MCP access following `docs/FIGMA-PUBLISH-RUNBOOK.md`. See `.claude/skills/audit-run/SKILL.md` for the full reusable procedure, Figma step included.

**Automatic, every run, no further steps:**
- **C2 (`data.json`)** — the canonical audit truth. Every other output derives from this alone, never a separate calculation.
- **Excel** (`report.xlsx`) — the complete structured report (v1.0 §15's tab set).
- **Standalone HTML** (`report.html`) — a self-contained single-file rendering of the same dashboard content, every screenshot embedded as a `data:` URI (`src/agents/c1-html-reporter/index.ts`) — opens by double-click, no server, portable to another machine. A `report-package.zip` fallback is added only if the embedded file would exceed 25MB.
- **Local Audit Dashboard** — served at `http://localhost:<port>/projects/<project-name>/runs/<run_id>`. Reads the same C2 JSON as everything else — never a separate calculation.

**Persisted automatically, but requires a live Claude Code + Figma-MCP session to actually publish:**
- **`figma-plan.json`** — the full deterministic plan: `00 Overview` … `08 Needs Review` tables, PLUS the approved interactive-marker system per page audit (`pageAudits[].markerGroups` — curated, deduplicated, root-cause-aware; see Decision Log #32) and `globalComponents` (Header/Navbar/Footer representatives).
- **`figma-composite-plan.json`** — per page, the measured sticky-header height and the exact tile crop/placement geometry a live publish should use to assemble the full-page capture without repeating the header or shipping one oversized raster.
- Actually writing these to Figma (creating the file, building pages, uploading real screenshots, wiring the Default/Hover interactive marker components and their hover reactions) is `docs/FIGMA-PUBLISH-RUNBOOK.md`'s job, executed by a Claude Code session with Figma MCP tools — never a bare CLI command, and never mandatory for a run to be considered complete.

**JSON (`data.json`) and raw screenshots are internal/backing data** — not deliverables themselves, though the dashboard and HTML report read them directly. JSON feeds re-audit diffing, Excel, HTML, the dashboard, and both Figma plan artifacts; screenshots back the HTML report's embedded evidence, the dashboard's evidence view, and whatever a live Figma publish uploads.
