# Figma Publish Runbook (Decision Log #32, codified — hover-visibility fix Decision Log #34)

**Audience:** a Claude Code session with live Figma MCP tool access (`use_figma`, `create_new_file`, `upload_assets`, `get_screenshot`, etc.) — never a bare CLI command, and never the headless Claude Code path (`src/figma/publish.ts`/`prompt-contract.ts`'s `buildPublishInstruction`, a different, confirmed-failed, LEGACY path — see those files' headers).

**Why this exists, and why it's short:** the interactive-marker Figma system (curated root-cause markers, hover annotation cards, sticky-header-safe full-page composites) was built and proven correct by hand against one real run (`market-entry-real-1`). Every rule discovered during that pass — dedup, tiling, marker Y-clamping, `clipsContent`, Legend+list placement, blank-image prevention — is now **code**, not prose:

- **What to build**: `src/figma/publish-plan.ts` (marker dedup, colors, content) + `src/figma/page-composite-plan.ts` (tiling geometry) → `figma-plan.json` / `figma-composite-plan.json`.
- **Exactly which operations to perform, in order, with every rule baked into the data**: `src/figma/publish-ops.ts` → `figma-ops.json`. `clipsContent: false` is a literal field on every marker component-set op, not a step to remember. Every image-upload op past the first tile is pre-cropped by the measured header height — a raw, uncropped tile can never be emitted. Every marker's placed Y is pre-clamped ≥ 0. The Legend panel and its numbered list are the SAME operation, so they cannot land after the Footer or as a detached panel.
- **What to verify, against what actually came back**: `src/figma/publish-verify.ts` — `checkBlankImage`, `checkHoverCardNotClipped`, `checkBounds`, `checkMarkerTraceability`, `checkLegendPlacement`, `checkNoMatchMarkers`, `checkComponentLibraryHidden`.

This runbook is now just the **mechanical replay procedure** over `figma-ops.json` — there is no remaining judgment call about which findings matter, where a marker goes, what a card says, or how to crop a tile. If something looks wrong, it's a bug in `publish-ops.ts`/`publish-plan.ts`/`page-composite-plan.ts` (fix it there, add a regression test to `test/unit/figma-publish-ops.test.ts` — never patch the Figma file by hand and call it done.

## Inputs (already on disk — regenerate with `pnpm run agent figma-plan <runId>` if stale, never by hand)

For run `<runId>` under `projects/<project>/runs/<runId>/`:
- `data.json` — C2, the canonical audit truth.
- `figma-ops.json` — a `FigmaOperationPlan` (`src/figma/publish-ops.ts`): `ops[]` (typed, ordered — `EnsureFile`, `EnsurePage`, `CreatePageAuditFrame`, `UploadTileBlock`, `CreateMarkerComponentSet`, `PlaceMarkerInstance`, `WireHoverReaction`, `StageComponentLibrary`, `CreateLegendPanel`, plus content ops for pages 00/02–05), `coverageGaps[]` (markers that could not be placed — never faked), `missingCompositePlanFor[]` (pages skipped entirely because no tiles exist).
- `figma-plan.json` / `figma-composite-plan.json` — the underlying content/geometry `figma-ops.json` was built from; read only if you need more context than an op already carries.
- `screenshots/<pageId>/page-tile-N.png` — the raw tiles `UploadTileBlock` ops crop from.
- `screenshots/<pageId>/s<N>-<M>-element.png` — per-finding element crops, used as marker evidence.
- `project.json` — `figmaFileKey`/`figmaFileUrl` if a file already exists for this project (republish target, `EnsureFile.mode === 'mutate'`); `figmaTeamPlanKey` for creating a new one (`EnsureFile.mode === 'create'`).

## Step 0 — Load skills, confirm access

1. Load `figma-create-new-file` and `figma-use` skills (mandatory before their respective tools, per those skills' own instructions).
2. Call `whoami`. If it fails or the team plan key doesn't match `project.json.figmaTeamPlanKey`, stop and tell the user — do not guess a team.
3. If no live, authenticated Figma MCP session is available at all, stop here and report that plainly (Step 5) — do not attempt the headless path as a substitute; it is a different, confirmed-failed mechanism (IMPLEMENTATION-PLAN.md §6 Spike 3).

## Step 1 — Replay `figma-ops.json`, one op per real MCP tool call

Iterate `ops[]` in order. Each op maps to exactly one MCP tool call:

| Op | Tool call |
|---|---|
| `EnsureFile` | `mode: 'create'` → `create_new_file` in `figmaTeamPlanKey`'s team; record the returned `file_key`/`file_url`. `mode: 'mutate'` → operate inside the existing `figmaFileKey` file; never create a second one. |
| `EnsurePage` | Switch to/create the named page (`figma.setCurrentPageAsync`, never assign `figma.currentPage`). |
| `CreatePageAuditFrame` | Create a frame `widthPx × heightPx`, and set its `clipsContent` to the op's own `clipsContent` field (`false`) immediately. |
| `UploadTileBlock` | Crop `tilePath` to `[sourceCropY, sourceCropY + sourceCropHeight)` (`cropTileForBlock` in `page-composite-plan.ts` if replaying outside a live session that already has the bytes) and `upload_assets` it onto a rectangle at `(destX, destY)` sized `widthPx × sourceCropHeight`. |
| `CreateMarkerComponentSet` | Build the Default/Hover variant pair from `hoverCard`'s fields verbatim (`shortName`, `status`, `severityText`, `explanation`, `bullets`, `dsLine`, `findingLabel` — do not invent or omit any). `combineAsVariants`, then **immediately** set `clipsContent = false` on the result AND leave/set `visible = true` — the op's own fields are the reminder, not a step to skip. **Decision Log #34 — do not hide this, ever:** an earlier version of this runbook instructed setting `visible = false` here, reasoning that a component's own visibility is independent of its instances' rendering and of variant-swap `CHANGE_TO` prototyping. That reasoning was live-tested and found WRONG: Figma's Presentation/Prototype-mode hover-swap silently fails to navigate to a destination variant whose component SET is hidden, even though the reaction data is completely valid and reads back fine from the Plugin API — confirmed by A/B diagnosis against the working `market-entry-real-1` reference (masters `visible: true`) vs. `brand-perception-survey-page`/`survey-page-audit`/an initial `report-store-page` build (masters `visible: false`, hover broken on every single marker in all three). Isolation from the report relies ONLY on `StageComponentLibrary`'s horizontal position now — never on hiding. |
| `PlaceMarkerInstance` | Place the Default variant at `(x, y)` — `y` is already clamped ≥ 0, use it as given. |
| `WireHoverReaction` | `instance.reactions = [{ trigger: { type: 'ON_HOVER' }, actions: [{ type: 'NODE', destinationId: <hoverVariantId>, navigation: 'CHANGE_TO', transition: { type: 'SMART_ANIMATE', easing: { type: 'EASE_OUT' }, duration: 0.15 }, resetVideoPosition: false, resetScrollPosition: true }] }]` — match `market-entry-real-1`'s live transition values exactly (`SMART_ANIMATE` / `EASE_OUT` / `0.15`s), not `transition: null` and not an improvised duration; Figma normalizes the reaction's exact field names on write (`resetScrollPosition`/`resetVideoPosition`, not e.g. `preserveScrollPosition`) — pass them as shown here rather than guessing. |
| `StageComponentLibrary` | Move every component set's master to `(x, y: 0)` from the op — **to the right of the Legend** (`x >= legend.x + legend.widthPx`), never below the frame. Wrap all of them in one Figma Section named `sectionLabel` from the op, and leave/set `section.visible = true` — the op's own `visible: true` field is the reminder. **Decision Log #34 — never hide the Section (or its members) either:** the three-round regression history below led to hiding as the "fix," which then broke hover entirely (see the `CreateMarkerComponentSet` row above) — the actual, final fix is horizontal position alone. **Regression history (four rounds now):** (1) an earlier version staged these at `y: totalHeightPx + 5000` — still "far away" on paper, but on the SAME vertical axis a reader scrolls down to read the report; the first time a real multi-tile page (brand-perception-survey-page) was actually scrolled, this rendered as a visible duplicate numbered findings list after the Footer — fixed by horizontal staging. (2) Horizontal staging alone still left the Section discoverable by deliberately scrolling/zooming the Figma canvas sideways on brand-perception-survey-page and survey-page-audit — (3) hiding the Section, and then hiding every individual marker master too (Figma Sections auto-manage membership by geometry and can silently eject an overflowing member as a visible top-level sibling), was tried next and DID stop the visual leak — but (4) it also silently broke `CHANGE_TO` hover-swap for every marker in the file, discovered only when a human tried Present mode. The accepted, final tradeoff (matching `market-entry-real-1`, the one file that has always worked): stay visible, rely on horizontal distance from the Legend for isolation, accept that a reader who deliberately scrolls far enough sideways in the Figma canvas (never in a normal vertical read, never in an exported screenshot of just the frame) could find it. |
| `CreateLegendPanel` | Build the panel at `(x, y)`, sized `widthPx`, with `title` (the page URL) and `colorKeyLine` verbatim at the top — unchanged from before (Decision Log #33 only changed the per-finding rows and the capture note, never the panel's own bg/border/radius/padding/URL header/color key). Then `lines` **verbatim, in order** — this IS the compact numbered list, directly under the color key, never a separate node placed elsewhere. **Per-row treatment (Decision Log #33, "richer Market Entry treatment" — do not skip either line):** each `lines[]` entry is a small vertical stack, NO colored dot/ellipse (Market Entry's own Legend has none — the colored TEXT is the only indicator): (1) `primary` as ONE Semi Bold ~12.5px text node, colored by mapping the op's own symbolic `color` (RED/ORANGE/AMBER/GRAY — same field every other op uses) to the **Legend-text hex palette** — RED `#b01f24`, ORANGE `#d97321`, AMBER `#c9992e`, GRAY `#666666` — **deliberately different from** the marker-circle/hover-card hex palette (`#e53c3c`/`#f27e21`/`#edb326`/`#8a8b92`); (2) `secondary` as a second Regular ~10.5px text node, always `#666` regardless of `color` — never colored, never merged into the primary line. This is the numbered list's ONLY home on the page — if you ever find yourself placing a second numbered list anywhere else (including "for symmetry" near the Footer), stop: that is exactly the bug `StageComponentLibrary`'s regression history above describes. **Capture note:** when `captureNote` is non-null, build ONE small bordered card below the rows — bg `#f8f6f1`, border 1px `#ebdead`, radius 6px, padding 12/10, gap 4, a bold 11px black "Capture note" title, then `captureNote`'s text verbatim as an 10.5px `#666` body (the same clean card treatment as Market Entry's own capture note) — when `captureNote` is `null`, build NOTHING here; do not invent a note, and do not keep the old bare gray text line. |
| `CreateSummaryTiles` | 00 Overview's colored stat tiles (RED/GREEN/AMBER/GRAY/BLACK per `summaryTileColor`) — never a plain table. |
| `CreateRootCauseCards` | 02 Root Causes — one stacked card per page-wide rule/property dedup (`buildRootCauseCards`): title, category pill, occurrence pill, explanation, affected-types/expected footer. Matches the approved reference file (market-entry-real-1) exactly — never the flat `pages['02 Global Issues']` rows. |
| `CreateComponentFindingCards` | 03 Component Findings — one evidence card per `markerGroups` entry, same numbering as the Page Audit markers: thumbnail, `cardColor` status pill (2-tone: RED=Incorrect, AMBER=everything else — see `cardStatusColor`), severity/confidence/section pills, actual→expected (with a "(N properties total)" note when truncated), recommendation, C2 finding id. |
| `CreateNeedsReviewCards` | 04 Needs Review — curated, diversity-sampled cards (`buildNeedsReviewCards`): thumbnail, amber status pill, confidence, reason, possible DS matches. Never every raw row — `shown`/`total` on the op make the curation explicit. |
| `CreateGlobalComponentCards` | 05 Global Components — Header/Footer evidence cards (thumbnail + status pill + note), now covering all four marker-eligible statuses (widened `selectGlobalComponents`), not just INCORRECT/DEVIATION. |

**Tile/card hex palette (pages 00, 02, 03, 04, 05):** `CreateSummaryTiles`, `CreateRootCauseCards`, `CreateComponentFindingCards`, `CreateNeedsReviewCards`, and `CreateGlobalComponentCards` all carry a symbolic `RED`/`GREEN`/`AMBER`/`GRAY`/`BLACK` color (never `ORANGE`, which is reserved for page 01's markers/Legend below). Map it to hex via `TILE_CARD_COLORS` (`src/figma/publish-ops.ts`) — RED `#b01f24`, GREEN `#3f7d58`, AMBER `#c99a2e`, GRAY `#6b7280`, BLACK `#000000`. These are deliberately the SAME values as the HTML dashboard's `STATUS_COLORS` (`src/dashboard/views/render.ts`) — reused rather than re-specified, since a live publish of the "industry-report" run (2026-09-17) already reached for that exact palette once it turned out nothing Figma-side specified these pages' colors, and `TILE_CARD_COLORS` now makes that the actual, single-sourced contract. This is a DIFFERENT hex set from page 01's Legend-text and marker-circle palettes below — those are their own separate, reference-verified conventions for a different (spatial marker/hover-card) visual treatment; never cross-apply either direction.

**Text-node gotcha (hit once building brand-perception-survey-page's card pages, now avoid it):** when creating a wrapping `TEXT` node, set `.characters` **before** `.textAutoResize = 'HEIGHT'` — setting the mode first, while the node is still empty, locks in a zero width and the node's height balloons into the thousands of pixels on layout. Append to the parent and set `layoutSizingHorizontal = 'FILL'` only after `.characters` and `.textAutoResize` are both set.

Report (don't silently drop) every entry in `coverageGaps` and `missingCompositePlanFor` — these are real, already-identified limits of what could be captured, not something to paper over.

## Step 2 — Mandatory verification (never skip, never report success without doing this)

Call `src/figma/publish-verify.ts`'s functions on what actually came back — not by eyeballing:

1. **`checkBlankImage`** per uploaded tile: `get_screenshot` it back, decode, compute `{mean, stdev}`. A near-zero stdev is the confirmed blank/gray failure mode (IMPLEMENTATION-PLAN.md §6 Spike 1) — stop and report the exact failure, do not report the publish as complete.
2. **`checkHoverCardNotClipped`** per marker: `get_screenshot` the Hover variant directly, measure its rendered height against the expected card height.
3. **`checkBounds`** for every top-level child of the page-audit frame and the Legend.
4. **`checkMarkerTraceability`**: the placed finding ids must exactly equal `figma-plan.json`'s `pageAudits[i].markerGroups` ids — no invented, dropped, or renumbered markers.
5. **`checkLegendPlacement`**: the Legend sits to the right of the frame, and no stray list content exists anywhere else (e.g. after the Footer).
6. **`checkNoMatchMarkers`**: every placed marker color is RED/ORANGE/AMBER/GRAY — never a MATCH-colored marker.
7. **`checkComponentLibraryVisible`**: the marker-master/component-library Section AND every individual marker master must have `visible: true` (Decision Log #34 — inverted from the old, disproven `checkComponentLibraryHidden`; hiding any of these breaks hover, see the `CreateMarkerComponentSet`/`StageComponentLibrary` rows above).
8. **Live hover-integrity checks (Decision Log #34 — mandatory, query the PUBLISHED file, never rely on `figma-ops.json` alone for these):** for every placed marker instance, `use_figma` to read back `instance.reactions`, `await instance.getMainComponentAsync()`, and walk the destination's ancestor chain, then call:
   - **`checkMarkerHasHoverReaction`** — fails if a marker instance has zero reactions, or has reactions but none is `ON_HOVER`.
   - **`checkHoverTargetResolvable`** — fails if the reaction's `destinationId` doesn't resolve to a real node, OR that node exists but is `visible: false`, OR any ancestor up to the page (its component set, any wrapping Section) is `visible: false`. A node ID that merely *exists* is not "resolvable" in the sense that matters — Presentation mode still won't navigate to it if hidden.
   - **`checkMarkerComponentSetValid`** — fails if `instance.getMainComponentAsync()` returns null (detached/missing component), or if that component's parent is not a `COMPONENT_SET` (no Default/Hover pair to swap between).
   - **`checkMarkerReactionCountMatches`** — fails if the number of placed marker instances doesn't exactly equal the number carrying a valid `ON_HOVER` reaction (catches a marker silently placed without ever being wired, even when `checkMarkerTraceability` — which only checks finding ids — passes).
   Pass all of this into `buildVerificationReport`'s `liveMarkerHoverRecords` input (or call `buildLiveHoverVerificationReport` directly) — never skip it because `figma-ops.json` already "looks right" on paper; that is exactly what looked right on all three broken files before this diagnosis.

Write the aggregated result (`buildVerificationReport`, one call per page) to `figma-verification.json` alongside the run's other outputs.

## Step 3 — Report back

Exactly the fields the operator needs: Figma file URL, pages/sections created, marker count per page, root-cause group count, the Step 2 PASS/FAIL table (with the pixel-variance/bounds/traceability evidence, not just "looked fine"), and any `coverageGaps`/`missingCompositePlanFor` entries. If Step 2 finds a real problem, report it plainly — never silently patch over a failure by calling it done anyway. Then write the real `figmaFileKey`/`figmaFileUrl` back into `project.json`.

## Known, still-open limitations (be upfront about these, don't paper over them)

- The headless Claude Code publish path (`src/figma/publish.ts`, `prompt-contract.ts`'s `buildPublishInstruction`) remains genuinely blocked on Figma auth (IMPLEMENTATION-PLAN.md §6, Spike 3) — LEGACY, do not extend, this runbook does not fix that, it's a different path entirely (text-instruction, no image upload, no interactive components).
- `page-composite-plan.ts`'s header-height detection (`detectRepeatedBandHeight`) is tuned against one real page's contrast profile (`highDiffThreshold: 150`). A page with a much lower-contrast header/content boundary could need a different threshold — if the detected height looks wrong (e.g. 0 on a page you can see has a sticky header, or absurdly large), pass an explicit override rather than trusting a bad auto-detection blindly, then regenerate with `pnpm run agent figma-plan <runId>`.
- There is still no CLI `publish` command (OUT-4, a deliberate scope decision, not an oversight) — Figma's write API needs a live, authenticated interactive session; a headless process cannot do it (confirmed, not a choice). This runbook is the supported path to an actual Figma write.
