# audit-run — the one reusable procedure for every future audit

**Read this whole file before doing anything.** It exists so a normal "test this new page" request never turns into an architecture discussion. If you find yourself about to redesign a graph node, rename an output, or change scoring logic to make a run "work," stop — that is out of scope for this skill. File a note for the user instead of improvising.

## What you take from the user

Exactly three things, no more:
1. **`url`** — the exact page (single-page mode) or site root (full-site mode).
2. **`mode`** — `single-page` or `full-site`, **stated explicitly by the user**. Never infer it from the URL's shape (a URL that looks like a homepage is not evidence for `full-site` — ARCHITECTURE.md §0 is explicit that mode is the sole routing source of truth). If the user didn't state a mode, ask — don't guess.
3. **An optional run name** — the exact human-readable string the user gives (e.g. "Brand Perception survey page"), preserved verbatim as the run's display name (see "Project/output path & run naming" below). If the user gives none, one is auto-derived from the URL — never a bare `run-<timestamp>-<random>` id standing in as the visible name.

Everything else — AI mode, Design System path, output locations, Figma team, dashboard port — already comes from `audit-agent.config.json` / environment and needs no per-run input. Do not ask the user for it.

## Project/output path & run naming (locked)

**Output location is fully automatic — never ask the user for a save path.** Every run lands under this standalone repo's own `projects/` directory: `audit-agent/projects/<project-slug>/runs/<run-id>/` (`<project-slug>` = `projectNameFor(url)`, a slugified hostname+path). `mode` alone routes to `audit-page` (single-page) or `audit-site` (full-site) — never inferred from the URL.

**Display name vs. run id — two different strings, never conflated:**
- **Display name** — exactly what the user typed as the run name (or, absent one, a name auto-derived from the URL by `resolveRunName`, e.g. `/brand-perception-survey` → "Brand Perception Survey"). This is what appears as the Figma file name and the friendly report filenames — never slugified, never replaced.
- **Run id** — a filesystem/DB/Figma-node-safe slug derived FROM the display name (`resolveRunName`'s `runId`, e.g. "Brand Perception survey page" → `brand-perception-survey-page`) — this is the folder name and the `--run-id` value.

Pass the user's run name via `--run-name "<name>"` on `audit-page`/`audit-site` (the id is auto-derived; `--run-id` remains available separately as a power-user override of the folder slug only — it never touches the display name). Both names are persisted to `run.json` in the run folder (`writeRunMeta`/`readRunMeta`, `src/output/run-store.ts`) so a later `figma-plan <runId>` regeneration still uses the right display name without asking again.

**Before running, print — then proceed automatically, no approval wait:**
```
Project folder: <paths.projectDir>
Run name:       <displayName>
Run ID:         <runId>
Run folder:     <paths.runDir>
```
This is already wired into `audit-page`/`audit-site`'s CLI output, first thing after the names are resolved — verify it printed, don't just assume.

**Report filenames** — `report.html` and `data.json` remain the canonical fixed names. The CLI also writes a friendly HTML copy using the display name (e.g. `Brand Perception survey page.html`). Never rename the canonical files. **Excel output is disabled by explicit project preference:** do not generate `report.xlsx` or friendly `.xlsx` copies, regenerate legacy Excel files, or offer Excel as a current deliverable. Existing historical files can remain; their presence does not make them a current output.

## Report formatting rule — an Expected typography value in `rem` always shows its px (permanent, every report surface)

**The rule.** Whenever an Expected **typography** value is stored or shown in `rem`, every report displays the resolved px beside it, in exactly this spelling: **`2.441rem (39.06px)`**. "Typography" is `font-size`, `line-height`, `letter-spacing`, `word-spacing` and `text-indent` (and a compound part of them, such as `label.font-size`) — `TYPOGRAPHY_LENGTH_PROPERTIES` in `src/output/display-values.ts`, the one place to widen it. Everything else is shown exactly as before: a token name (`--text-lg`), an `em` value (`-0.01em`), a keyword, a compound value, "Not resolved", and a `rem` value of a NON-typography property (padding, gap, radius, width).

**Display formatting only — nothing stored changes.** `data.json` (C2) keeps the audit's own values: the DS token/value, the finding's `expected` / `expectedToken`, its status, the matching and nearest-match result, and the recommendation TEXT are byte-identical whether or not a report was drawn. Report layers call two pure, idempotent functions when they draw a string (`src/output/display-values.ts`):
- `expectedForDisplay(property, expected, rootFontSizePx?)` — (`rootFontSizePx` = the measured root of the finding's page, see "Root context") a structured Expected value: the compact "actual → expected" summary, the detail view's Expected field, every cell of a property comparison table (including a "Candidate only" unresolved reading), the Figma plan's actual → expected lines, the Excel Expected columns.
- `recommendationForDisplay(text, rootFontSizePx?)` — recommendation / detail prose that quotes an Expected value in B4's one format `<property>: <actual> → <expected>` (`font-size: 32px → 1.953rem` → `font-size: 32px → 1.953rem (31.25px)`). B4's own nearest-size annotation (`1.953rem (31.25px — the closest DS size, 0.75px away)`) already carries the px and is left alone.

Both use the audit's OWN conversion (`lengthToPx`: rem × the root font size of THAT page) and spelling (`formatPx`: ≤ 2 decimals, trailing zeros dropped) — no value is hardcoded, so every future size converts the same way.

**Surfaces — all of them go through those two functions, none re-implements the formatting:** the HTML report and live dashboard (`src/dashboard/views/render.ts`: compact summary, detail Expected field, property comparison table, recommendation / note views, the root-cause table), the Figma plan (`src/figma/publish-plan.ts`: marker-card bullets, actual-vs-expected lines, root-cause "expected", recommendation / reason text) and the Excel report (`src/agents/c1-excel-reporter/index.ts`: Expected, actual-vs-expected, recommendation / note columns). A NEW report surface that prints an Expected value or recommendation must route it through them, passing the finding's page root (`pageRoots(data).of(finding)`). C2 / `data.json` never formats anything.

**Root context — the page's MEASURED root font size, never an assumed 16px.** A `rem` length resolves against the root font size of the page it is drawn on, so the px beside an expected `rem` value is that value × the root the audit MEASURED on that page. The capture reads it once per page (`readRootFontSizePx`, `src/t-layer/computed-style.ts` — the very expression `extractComputedStyle` attaches to every element B3/B4 compare, so the root a report converts with is the root the audit compared with: on a 20px-root page B4's own `(39.06px — the closest DS size …)` annotation and the display agree, `test/integration/page-root-font-size.test.ts`), carries it in the page's capture summary (`PageResult.capture.rootFontSizePx`), and C2 persists it per page as `pageSummary[].rootFontSizePx` in `data.json` — additive and optional, like `aiMode`. Every surface builds `pageRoots(data)` once and passes `roots.of(finding)` (the root of the page the finding belongs to; `roots.ofUrl(url)` for an aggregate row that carries only a URL) as `rootFontSizePx`. An aggregate row (a global issue, a root-cause card) quotes its example / representative finding, so its px are that finding's page's. The measurement is context only: it decides nothing in matching, status or any finding (no engine file is touched — engine revision unchanged), and a recorded value that cannot be a root (0, negative, NaN) is ignored.

**The one case a root is assumed** is `FALLBACK_ROOT_FONT_SIZE_PX` (16 — the browser default, and the converter's own default): only for a run that recorded none — a `data.json` written before the measurement was persisted, or a page record restored from the database after a restart. Such a run shows its px at 16, so on a page that really overrode its root the px are not that page's; re-audit to record the real root. A page reused unchanged (§4.4) carries the root measured on THIS run's fresh capture.

**Versions.** Adding this rule changed what both locked templates render — every Expected typography `rem` now carries its px, so the same `data.json` draws differently — which is a template change under "Template contracts", so it bumped both stamps: `HTML_TEMPLATE_VERSION` → `html-report-v11` and `FIGMA_CONTRACT_VERSION` → `figma-layout-v5` (the repo's own precedent for a report-layer change to what a template prints: v8 candidate values, v10 evidence display). A `report.html` or `figma-plan.json` stamped v10 / v4 shows bare `rem` values (written before the rule); v11 / v5 — and every later stamp (v12 / v6 added the Coverage Gate, not a change to this rule) — shows the px. The Excel report has no version stamp (and is not a current deliverable). **Any later change to the rule** — its scope (`TYPOGRAPHY_LENGTH_PROPERTIES`), its spelling, the surfaces that carry it — is a template change again: bump the stamp of each template it touches, update the pinned tests (`test/integration/c1-html-report.test.ts` for HTML, `test/integration/cli-e2e.test.ts` for Figma) and this section. How the root is MEASURED is capture data, not template: a different measurement changes `data.json`, never a stamp.

**Coupling to keep:** the recommendation prose B4 writes is what `recommendationForDisplay` reads. `test/unit/display-values.test.ts` builds a finding through B4's own `buildFinding`, so a change to B4's `<property>: <actual> → <expected>` format fails there instead of silently dropping the px.

Regression coverage: `test/unit/display-values.test.ts` (the properties, the conversion and root, idempotence, non-rem / non-typography left alone, the B4 format coupling), `test/unit/report-rem-px.test.ts` (the HTML report: summary, detail, table, recommendation view, measured roots, stored data untouched), `test/integration/report-rem-px-surfaces.test.ts` (the Figma plan and the Excel report, per-page roots across all surfaces, and that all surfaces agree while `data.json` stays the audit's own) and `test/integration/page-root-font-size.test.ts` (real Chromium: the capture measures 16 / 20 / 10px roots, the per-element and per-page reads agree, two pages with different roots in one run each convert with their own, B4's annotation agrees with the display).

## Component identity vs. compliance (every future audit, not a page-specific fix)

**Component identity is determined before compliance.** For every production element belonging to a Design System rule-mapped family (`RULE_CANDIDATES` in `src/agents/b3-ds-matcher/deterministic.ts`: button, icon-button, link, nav-link, card, badge, tag, chip, section-heading, eyebrow, input, search), B3 decides WHICH existing DS component/variant it is trying to be from its own structure (tag, ARIA role, real rendering facts — B2's `detectionConfidence`, never color alone) — and only THEN measures how well it complies. A CTA that is evidently a Button does not stop being a Button because its color, gradient, shadow, radius and typeface are all wrong: those differences are exactly what the audit exists to report.

**Existing DS components are corrected to their closest valid existing variant; they are not recreated as New Components because production styling differs.** Concretely, permanently:
- Existing DS component + wrong styling/font/color/gradient/border/radius/arrow/animation ≠ New Component.
- Existing DS component + uncertain exact variant ≠ automatically New Component either — the family is kept, only the specific variant choice may ever need a human (the compatible candidate may be shown for review, but unobserved state or unresolved compound-slot identity must not become a mandatory visual correction).
- Low compliance (even 0%) must never destroy a strong component-family identity match — B4 already audits whatever `dsComponent` B3 hands it, against the FULL set of properties the Design System source actually governs for the matched variant (`src/ds/component-styles.ts`'s static analysis of the real `.tsx` source — every real CTA/Button property: background, gradient, effect/shadow, border, radius, typography, spacing/gap, layout), and reports every real difference as DEVIATION/INCORRECT. **B6 (`src/agents/b6-new-component-evaluator`) only ever receives an element when B3 found no such family at all** — never merely because compliance was low.
- **A role-less element whose type is decided from its own structure still claims its family.** A bordered/filled text leaf → badge, a repeated card-scale block with a visible surface → card (B2 marks these `structural`): their detection confidence stays LOW because no role backs it, but the structure IS the pattern the DS family is defined by, so B3 maps them to Badge / Card (the closest existing variant; wrong radius, colours, type and padding are B4 deviations) instead of leaving them undecided for B6. Only a doubtful TYPE — an unlabelled clickable inferred to be a button, a transparent overlay — may not claim a family. An element B5 recovers takes exactly this path (see "Coverage: …" below): `Recovered ≠ New Component`.
- What genuinely is NOT measured today (never fabricated, never silently ignored either): the specific icon/arrow SHAPE or direction (only structural signals like icon presence and icon/text `gap` are compared), hover/focus/active/pressed/disabled STATE style values (only the rest state is captured), and DS-defined motion/animation (extracted from the DS source during static analysis but not yet exposed for comparison — a known, stated gap, not a silent one).
- **Not by color alone.** Family identity always comes from the element's own structure/role (B2's detection, independent of color) plus the DS's own rule mapping for that type — a red decorative element that isn't structurally a button/CTA is never coerced into one.

Regression coverage: `test/unit/b3-family-identity.test.ts` (identity-vs-compliance, variant selection, ties, never-B6-for-low-compliance, genuine-new-component-still-reaches-B6, color-alone exclusion), `test/unit/b3-family-search.test.ts` (the badge/card families, the deeper search, structural types) and `test/integration/no-api-audit.test.ts` (the same principle exercised through a real browser + the real Design System). If you find yourself tempted to route a badly-implemented-but-clearly-identifiable CTA to "new component" territory to make a run "look clean," that is exactly the bug this section exists to prevent — fix the underlying measurement/evidence, never the classification.

## Nearest-match precedence (every numeric Design System value the audit recommends — not only font-size)

Whenever the audit has to say *which Design System value* a measured number should become, it resolves it in this fixed order and stops at the first step that answers:

1. **Exact matched component value.** The element is identified as an existing DS component/variant (B3) → that variant's own value for the property is the contract and is used as is, whether or not the element matches it. `Button / primary / md / light` requires `radius: 5px` → the finding says 5px, never a "nearer" scale step. A value that already equals a DS value (distance 0, within the comparator's 0.5px tolerance) is a match and is preserved.
2. **Otherwise the nearest valid DS token of the correct token family.** Only when a foundation/token scale governs the property, several valid values exist, and no matched variant gives a more specific value. The recommendation is the single nearest step — radius `6px` on the scale `0 / 2.5 / 3 / 4 / 5 / 8 / 10 …` → `5px`; radius `8px` → `8px`; a `32px` heading among the DS heading sizes `31.25 / 39.06 / 48.83` → `31.25px` — never "use a DS token" and never a list of every step.
3. **Otherwise review — never a guess.** No scale for that property, an empty scale, a value that cannot be normalised (`calc()`/`clamp()`/`auto`, an undefined token) or an identity that cannot be decided: no value is invented. The property row is `UNRESOLVED` (shown "Not resolved" / "Not verified" with its reason); the element is `UNVERIFIED` (matched, nothing comparable) or `NEEDS_REVIEW` (identity undecided) and a reviewer decides. "NOT_RESOLVED" is shorthand for this — the stored statuses are exactly those names; do not add a new one.

Guardrails that make it safe to apply everywhere:
- **Correct token family only.** Candidates come from the property's own family and nowhere else: type size → the type scale (R1.3) · padding / margin / gap → the named spacing scale (R3.5) · radius → the radius scale (R3.6) · line-height → line-height tokens · letter-spacing → tracking tokens · a size governed by a DS size scale → that scale. A numerically close value from another family is never a candidate (a 16px font-size is not "matched" to the 16px spacing step), and aliases the DS itself marks as off-rhythm (R3.5's `--space-1…20`) are not valid candidates.
- **Never override an exact matched variant.** The matched variant's own comparison always wins for the properties it governs; a foundation scale only speaks for a property nothing more specific resolved (`filterFoundationViolations` in B4, which drops a foundation citation for any property the variant's comparison already settled — pass or mismatch).
- **Semantic identity ≠ visual/token matching.** What the element IS (tag, role, component family — B2/B3, identity before compliance) never changes because a value is near to, or far from, a token; and a nearer visual value never changes its tag or family. Nearest-match chooses a VALUE (or the variant whose value is nearest); it never reclassifies.
- **One unit before any distance.** The measured value and every candidate are normalised to the family's common unit first — lengths to px (`px` as is · `rem` × the page's root font size · `em` × the element's font size, only where safely resolvable), at the captured viewport — so rem, em and px values are compared like for like.
- **Deterministic ties.** Equally-close candidates are separated by component/context evidence → visual hierarchy → semantic level → the larger value (detail under "Typography" below).
- **One mechanism, no special cases.** Every wired property calls the same picker (`pickNearestSize`, `src/skills/nearest-typography.ts`) with ITS family's values. There is no per-property search and no per-page or per-tag branch. A new numeric family joins by adding its scale to the foundation context and a regression test — nothing else.
- **Same code for every audit.** Single-page, full-site and re-audit all run the shared B3/B4 page graph. A re-audit shows a changed variant as a baseline change (Decision Log #29), so a recommendation that moves to a nearer value is never mistaken for a regression or a resolution.

What "makes sense" for nearest matching: a numeric property, comparable after unit normalisation, governed by a scale of several valid values. What does not: a property a matched variant gives exactly one value (step 1 already answers), categorical values (colour, font-family, display and other keywords), and anything with no DS scale (→ step 3).

Enforced in code today (the code is the source of truth — if this list and `FoundationContext` in `foundation-rules.ts` disagree, correct the doc in the same change): font-size (heading level in B3, tied variants in B4 `compareAnyOf`, the R1.3 type scale), radius (R3.6), padding / margin / gap (R3.5), and the exact-variant precedence above. line-height, letter-spacing and width/height are compared only against the matched variant's single value (otherwise "Not resolved"); giving any of them a DS scale in the foundation context is the only step needed to put it under this rule.

## Heading role before nearest-size matching (locked — every future audit, not a page-specific fix; engine r4)

**The role of a heading-like text is decided from the section's whole text hierarchy, before any Design System component is chosen. `h1`/`h2`/`h3` is one signal, never the identity.** The three principles, permanently: `Supporting heading ≠ Main heading` · `HTML h2/h3 ≠ automatic SectionHeading` · `visual/semantic role must be identified before nearest-size matching`.

A typical structure — and the roles B2 gives it (the brand-perception-survey intro, the case this was found on): `ABOUT KEN SURVEY` (an `h2`, 10px/500, upper-case) → **eyebrow / supporting heading**; `Use real feedback from real audiences…` (a **`<p>`**, 30px Noto Serif 300 — the section's visually dominant text) → **main section heading**; `Built on Reach, Research, and Real Voices` (an `h3`, 16px/400 body copy) → **description / supporting copy**.

**Who decides what (no new agent, node or edge — B1 → B2 → B3 → B4/B6 → B5 unchanged):**
- **B2 — role.** `buildTypeContext` (`src/agents/b2-component-detector/deterministic.ts`) reads every candidate's real facts in the section FIRST (`detectDeterministically` is two-phase: read, then classify) and finds the dominant text — the largest non-numeral, non-control, non-owned text ≥ 24px; a real heading element wins a near-tie (≥ 95% of the max). `supportingRoleOf` then weighs, per element: size (≤ 14px, or ≤ half the dominant text), uppercase treatment (CSS or literal upper-case text), tracking, shortness (≤ 6 words / 40 chars), document order relative to the dominant text, weight, and — for the description reading — that it is not a card title / footer or nav label / clickable. Result: `eyebrow` (any tag — `h2`, `h3`, `p`, `span`; the CSS-uppercase/tracked ≤ 14px heading rule keeps working with no section context), `description` (a heading-tagged element that is body-sized, ≤ 400 weight, beside text ≥ 1.5× larger → type `paragraph`), or — for the dominant text when it is not already a heading, is a phrase (≥ 3 words, ≤ 200 chars) and is not in a footer/navigation — `main` (type `section-heading`, promoted even from a `<p>`). Stat numerals are never dominant. Each role is recorded on the component (`headingRole`) and as a `heading role: …` signal that B4 prints as a `ds-source` evidence entry on the finding, so a reviewer sees WHY the element is not a normal SectionHeading.
- **B3 — DS first.** The role picks the family: `eyebrow` → the DS eyebrow family (`RULE_CANDIDATES.eyebrow`, R4.8: `OverheadText`, `SectionLabel`), matched **ignoring the heading tag** (the DS roots are `<span>`/`<p>`; an `<h2>` eyebrow is not refused for its tag, exactly as a heading's tag never picks its SectionHeading size). **Locked colour rule:** on a neutral/light surface the eyebrow is the **Ken-red** text treatment (SectionLabel `style: text · variant: accent`, or OverheadText — both `--brand-red`), pinned in `decideMatch`; on a **dark** surface OverheadText (brand-red only, no inverse form) is not offered and SectionLabel's own dark tokens apply — red is never forced where readability needs the DS inverse treatment. A promoted `main` heading is matched as `SectionHeading` by **nearest rendered size** (the `h2` slot is only the tie-break proxy when the tag names none — and what the finding SAYS about the tag is the tag the element really has: a promoted `<p>` is described as "a <p> that is the section's main heading by its role … it stays a <p>", never as an `h2`); an element B2 did NOT promote never gets a heading slot from a `<p>` tag. `description` is body copy: foundation-only like any paragraph, never SectionHeading sizing.
- **B4.** Audits against the matched family's contract (font-size, weight, letter-spacing, colour, text-transform …) exactly as for any component, plus the foundation rules — with one exemption: **R1.2's "brand red is never heading text" does not apply to an `eyebrow`** (a heading tag on a supporting heading does not make it heading text; `checkFoundationRules`).
- **If the DS does not clearly define the pattern** (the family cannot represent the element → undecided, never forced into `SectionHeading`): **DS first → approved Project Aura reference second → NEEDS_REVIEW.** Since engine r5 the second step is engine code, not a procedure — see "Design System first, approved Project Aura reference second" below: the approved pages' own measured styling for the same semantic role (Report Store, Case Study, Competition Benchmarking) is consulted ONLY when the DS search came back undecided, and it is **reference-backed existing-pattern evidence, never a replacement for the DS** and never a verdict by itself.
- **B7 re-checks the role independently** of everything above (see "B7 — Final Audit Coverage & QA"): the same classifier is run over the COMPLETE page text hierarchy, and an element whose audited role disagrees with its independently derived role (`ABOUT KEN SURVEY` audited as `SectionHeading` while a larger dominant heading exists; a main heading rendered as a `<p>` that was never audited as a heading) is a role-classification inconsistency routed back to B2/B3 — never accepted because the tag looked right.
- **What the DS defines today for an eyebrow (OverheadText):** colour `--brand-red`, `--text-xs` (12.8px), `--font-weight-bold` (700), `--tracking-label-wide` (0.15em), `text-transform: uppercase`, `display: inline-flex` · `align-items: center`. **It sets no `line-height`** — the eyebrow inherits its surrounding line-height, and the approved Case Study's `.te-eyebrow-red` (12.8px / 400 / 1.57px tracking / uppercase / red) and Competition Benchmarking's `.label` (12px / 600 / 2.4px tracking / uppercase / red) set none either. State "line-height: not governed — inherits" rather than inventing a value.

**Limits, stated:** the reading is conservative by design — a small heading with no dominant text after it and no uppercase/tracking treatment stays a heading (never forced into `eyebrow`); a card title (repeated unit), a bold heading, a footer/nav label and a one-word wordmark are never reclassified; a section whose largest text is a real heading is never promoted over it. The eyebrow-by-section-context reading needs a dominant (≥ 24px) text after the eyebrow in the same B1 section; if B1 splits them across sections the eyebrow keeps the older uppercase/tracked rule only (B7's independent re-check reads the same per-section hierarchy, so it shares the limit — it reads it over every text item on the page rather than only B2's candidates).

Regression coverage: `test/unit/b-heading-roles.test.ts` (the section hierarchy and dominant text; eyebrow for h2/h3/p/span; CSS-uppercase kept; never forced; main promotion and its three refusals; description and its two refusals; B4's R1.2 eyebrow exemption; B3 against the REAL Design System: the h2 eyebrow reaches OverheadText/SectionLabel with Ken-red expected, dark surface never OverheadText, a promoted `<p>` is SectionHeading level 3 at 30px, an unpromoted `<p>` gets no slot) and, for B7's independent role check, `test/unit/b7-reconcile.test.ts` + `test/integration/b7-coverage-qa.test.ts` (a main heading rendered as a `<p>` that no stage audited as a heading is caught and corrected; an eyebrow audited as `SectionHeading` is caught and re-routed; `ABOUT KEN SURVEY` audited as an eyebrow with Ken red through the whole graph; a stat numeral and a supporting description are never silently excluded).

## Typography: the nearest Design System size, never the semantic level (the first application of the precedence above — every future audit, not a page-specific fix)

**The semantic HTML level and the Design System's visual typography variant are two different decisions.** An `<h2>` is an accessibility/hierarchy fact; which DS size it is audited against is a *visual* one. B3 therefore never names a heading's DS level (`SectionHeading` level 1/2/3) from its tag. It picks the level whose size is **numerically nearest the rendered size**, and the same nearest-size rule governs every typographic size the audit selects (`src/skills/nearest-typography.ts`, pure arithmetic, no page-specific branch).

The algorithm, for a numeric scale property (font-size):
1. Read the rendered value in px (computed `font-size`).
2. Normalise every valid DS size of the relevant component/family to px **at the captured viewport** — `expectationsFor` resolves SectionHeading's `text-[1.953rem] sm:text-[2.441rem]` for the width the page was captured at; `px` is taken as is, `rem` × the page's measured root font size, `em` × the element's own size (`lengthToPx` — the comparator's own conversion, so a candidate is exactly the value the comparison later checks).
3. The candidate with the smallest absolute px distance wins. Always — not "the first", not "the tag's".
4. Only candidates equally close (within 0.01px — rounding noise) are separated by anything else, in this order: **contextual/component evidence** (how many of the candidate's other governed properties — weight, tracking … — the element already fits) → **visual hierarchy** (the candidate that keeps the element's rank among the page's other headings) → **semantic heading level** (closest to the element's own tag) → the **larger** size (an element is never demoted on a coin-flip). A tie settled this way is published at lower confidence (0.7) and the rationale says it was a judgment call.

Worked example (the audit that prompted this): an `<h2>` at 32px. SectionHeading offers 31.25px (level 3, 1.953rem) and 39.06px (level 2, 2.441rem). 31.25px is 0.75px away, 39.06px is 7.06px away → the element is audited against **level 3** — `font-size: 32px → 1.953rem`, letter-spacing against level 3's `-0.01em` (every property comes from the SAME selected level, never mixed), severity LOW — and it **stays an h2**: the finding never recommends changing the HTML level to adopt a nearer visual size.

What every such finding shows: Actual · Closest DS value (px and the DS's own spelling) · Difference · DS source (file + variant) — as a note on the font-size row of the property table, in the recommendation (`font-size: 32px → 1.953rem (31.25px — the closest DS size, 0.75px away)` plus "The element is an h2 and stays one …") and as a `ds-source` evidence entry listing every size considered and what settled the choice.

Where it applies: B3 `nearestHeadingVariant` (heading level) → `DsMatch.visualSlot` / `DsMatch.typography`, read by B4; B4 `compareAnyOf` (equally-fitting variants of any matched component — e.g. a Button's sm/md/lg — publish the nearest font size, not the first listed; overall fit still comes first, nearest size is the tie-break among equally-fitting variants); the R1.3 type-scale check (one nearest step, never "a or b"). It is the same code for a single-page audit, a full-site audit, a re-audit and a new URL. A changed variant shows up in a re-audit as a baseline change ("compared against SectionHeading/level 3 this run, level 2 in run X", Decision Log #29), and because it changes what an audit reports it shipped under an engine-revision bump (`AUDIT_ENGINE_REVISION` — Decision Log #38/#39), so a full-site run never reuses findings an older engine produced (see "Engine revision & full-site reuse" below).

Regression coverage: `test/unit/nearest-typography.test.ts` (distance, px/rem normalisation, exact match, the tie chain), `test/unit/b3-nearest-heading.test.ts` (the heading cases against the real DS: 32px→level 3, 38px→level 2, h2 stays h2, exact sizes, equal-distance ties, viewport/root-font-size, never-invents-a-size), `test/unit/b4-nearest-typography.test.ts` (non-heading variants and R1.3) and `test/integration/typography-nearest-audit.test.ts` (the whole thing through a real browser: finding, property note, recommendation, evidence, report). If a heading looks wrong, fix the measurement or the candidate set — never add a per-page or per-tag exception.

## Coverage: section ownership, sampling, family search and B5 verification (every future audit's contract, not a page-specific fix)

**A measured violation can only be reported on an element the pipeline actually reached — and against the component it actually is.** Three real audits showed gaps that were never in B4's measurement — they were upstream, and each is fixed in the stage that owned it (Decision Log #40), never by widening a later stage to compensate:
- A real "Our Approach" `6px` radius and a decorative brand-red border, both unreported: B2's deterministic detector offered a candidate only for a heading, a form field or something clickable. A non-interactive styled status pill ("Phase 01" — no role, no `cursor:pointer`, just a bordered, filled `<div>`) was never even a *candidate*, so no rule — R3.6, R1.2, none of them — ever ran on it.
- "Differentiator" headings missing from the later rows of a page: B1 gave a sticky scroll stage the box of its (short) viewport window while its list rendered far below it, so those headings lay outside every section's y-range and were never offered to B2; and B2 capped **every** repeated group at 5, so the 6th heading of a 9-heading grid was sampled away.
- Elements B5 recovered, and a role-less badge: a recovered card skipped B3 and B6 entirely and was audited on foundation rules alone (19 of 33 on one real page ended UNVERIFIED, "Expected styles are not resolved"), and a badge — detected at LOW confidence because no role backs it — fell out of its own Badge family into B6 ("closest DS component Badge, 7 of 22 properties, too little to audit it as that component") purely because of how it was detected, so an existing component implemented wrongly was reported as an undecided one-off.

**Who guarantees what — one responsibility per stage, all inside the existing page graph `B1 → B2 → B3 → B4 → B5 → B6` (no new agent, node or edge was added for this; the order is unchanged — B5's recovery calls B2/B3/B4/B6's own functions in-process). B7, added after B6 by the later, explicit "final coverage" upgrade (Decision Log #45, below), only VERIFIES what these stages produced and routes a gap back to them; it never takes over any of their responsibilities:**
- **B1 — section ownership.** A section owns its band's y-range **and** its own DOM subtree. An element outside every band's y-range but inside a band's subtree (a sticky scroll stage, a clipped/overflowing panel — content rendered beyond its own box) is **adopted** by that section (`adoptedRefs`) and offered to B2 with it; the section's note says so ("N element(s) lie outside this section's y-range but inside its own subtree … are offered to B2 with it"). An element in no band's range and no band's subtree becomes its own section, or is noted "never offered to B2". A capture gap like this is a B1 fix — never a reason to widen B2.
- **B2 — detection and sampling.** A non-interactive status pill is found on the first pass (shape selects it: small, childless, text-bearing, not clickable; computed style confirms: a border or fill). Repeated groups are sampled **only when they are a real listing** — a B1-flagged listing section, or ≥ `LISTING_MIN_ITEMS` (12) members of one group in a section: the first `LISTING_SAMPLE_LIMIT` (5) are audited, the rest are counted in `coverage.sampledListings` (`sampled`, `totalObserved`) and stated in every report. A smaller repeated group — a 3-column feature grid of 9 headings, 7 nav links — is audited in full, every row. B2 also returns `decidedRefs`: every ref it made a decision about (captured, sampled out, excluded as an off-domain utility link, merged into another control, visually hidden, found not to be a candidate). Two types are decided from the element's own visible STRUCTURE (no role behind them, so the confidence stays LOW and the finding says so): a bordered/filled text leaf → `badge`, and — when B5 asks (`classifyCandidate` with `repeatedBlock`) — a repeated, card-scale non-interactive block → `card`, but only if it has a visible surface (border, fill, background image or shadow); a bare one is a layout column, excluded with its reason. Both are marked `structural`.
- **B3 → B4 — family search, then rules.** B3 decides which Design System family an element IS **before** it scores how well the element is styled (identity before compliance): the DS rule names the family for the type (R4.6 Badge, R4.3/R4.4 Card, R4.1 Button …), the rule's own files are searched first, and only when none of them can represent the element is the rest of the family searched (Badge/Tag/Chip/Pill/Label/Status found by name; the other R4.4 cards) — "no family" is never said before the whole family was tried. A LOW-confidence **structural** type (above) may claim its family; a doubtful TYPE (an unlabelled clickable inferred to be a button) may not. B3 records what it searched and why it answered as it did (`DsMatch.search`: the family and the basis — class fingerprint, rule fit, family identity, context slot, undecided), and for a family-identity match it never names a variant that itself paints brand red for a non-CTA element. An element left for B6 records why (`undecidedBecause`: no family for the type · the TYPE is only a low-confidence reading so the family was not claimed · classes point outside the family · the family cannot represent it), and B5's report lists each verified hand-off with that reason (`confirmedForB6`). B4 then audits a matched element against **that component's full contract** (radius, border, background/colour, typography, padding/gap, size, shadow/effect, state) and the foundation rules — heading level by nearest size, radius / spacing / type by nearest valid DS token (R3.6 / R3.5 / R1.3), forbidden decorative brand red on a non-CTA border or fill (R1.2) — see "Nearest-match precedence" and "R1.2" below. R1.2 is a prohibition, not a scale: for an element matched only by family identity its citation stands next to the variant's own mismatch rows.
- **B5 — final verification.** Per pass (at most 2) it checks three things and routes each gap to the stage that owns it (the rule below), records an honest outcome per item, and never re-captures what B2 declined on purpose — a B2 sampling or exclusion decision is policy, not a gap, and re-capturing it would undo the policy and contradict the coverage B2 reported.
- **B6 — only for a pattern no existing family represents.** `Recovered ≠ New Component` · `existing DS family + wrong styling ≠ New Component` · `existing DS family + uncertain exact variant ≠ B6`. An element B3 searched a family for and could not represent at all goes to B6 (its evaluation: `evaluateUnmatched`, `src/agents/b6-new-component-evaluator/evaluate.ts`); an existing component implemented wrongly is a B4 deviation. B6 is a claim about the Design System, and only a pattern no family represents may make it.

**The rule for every element B5 recovers or re-routes** (no new graph edge, no in-run cycle — Decision Log #13 is explicit that a `FeedbackEdge` is cross-run only; the graph order stays B4 → B5 → B6, and B5 calls the other stages' own functions in-process, never a parallel reimplementation):

```
B5 recovers or flags an element
  → B2 classifies it and captures its evidence          classifyCandidate + captureComponent (the first pass's own functions)
  → B3 searches the Design System family for its type    decideMatch — the answer AND the search are recorded (DsMatch.search)
       ├─ an existing family represents it  → B4 audits it against that component's FULL contract   deterministicEvaluations + buildFinding
       └─ no existing family represents it  → B6 evaluates it                                         evaluateUnmatched
  → B5 verifies the result — pass 2 only over what pass 1 touched — at most 2 passes, then NEEDS_REVIEW
```

The three checks each pass makes, and where each gap is routed:
- **Element coverage → B2.** Was every meaningful element audited, excluded with a reason, or explicitly unresolved? B5 re-derives candidates over whatever B2's first pass left unaccounted for (not a component, not in `decidedRefs`) in each section, two shapes, both geometry/structure-only (cheap, no premature style fetch): (a) **badge-shaped** — a small, childless, text-bearing leaf B2's own `isBadgeCandidateShape`/`decideType` path runs again over (the same function; a genuine second pass, normally finding nothing now that B2's first pass catches badges, but a safety net for a capture-timing quirk); (b) **repeated-block-shaped** — ≥2 same-size non-interactive generic siblings at card scale (`CARD_MIN_AREA`, 20,000 px²), put to B2's classifier as a possible card (a card only if it has a surface). A leaf with neither shape is never guessed into existence.
- **DS-matching coverage → B3.** Was the right family searched? B5 checks B3's recorded search against the family the DS names for the element's type (`verifyFamilySearch`): no record, a record of the wrong family, or a matched component outside the family with no class evidence behind it (an element built from another DS component carries that component's classes — that is legitimate) is a flagged answer. B5 re-asks B3 (at most twice per element) and re-routes the element by the new answer: an existing family → B4 audits it; none → B6 (B5 evaluates an element it recovered; the B6 node evaluates a first-pass one). B3 is deterministic, so a consistent answer is never re-asked, and an undecided result is recorded with B3's own reason — never a confident-looking guess manufactured to close the loop. A type the DS names no family for has nothing to verify: B6 is the right place for it. In today's pipeline B3 records its search on every answer, so this is a generic safety net, like the property check.
- **Property coverage → B4.** Were all applicable governed properties compared? Every matched component's foundation-rule coverage (R1.2 brand-red border/background, R1.3 type scale, R3.5 spacing scale, R3.6 radius scale) AND its matched variant's full contract — every governed property B4's own evaluation produces — is recomputed fresh and compared with what the finding shows; a genuine gap is corrected by rebuilding the finding via B4's own `buildFinding` (never a parallel finding-assembly path). In today's pipeline this is normally a no-op, but it is a real, generic safety net against a future regression, not a per-page special case. A subtitle candidate (`contextSlot: 'subtitle'`) is deliberately skipped, matching B4's own exclusion: its heading-vs-paragraph role is itself unresolved, so prescribing rules would be premature, not merely incomplete (caught live — omitting this guard turned a correct UNVERIFIED into a false INCORRECT).
- **No existing family → B6**, and only then. **Verified** → finalized as-is; nothing is touched.

**Outcomes — a valid exclusion is not an error.** For every element B5 tries to recover, `attemptRecovery` (`src/agents/b5-visual-verifier/completeness.ts`) records exactly one outcome:
- **recovered** — a real candidate, classified and captured, then routed like a first-pass element: B3 searches its family → B4 audits it against that component's full contract (`routedToB4`) or, only when no existing family represents it, B6 evaluates it (`routedToB6`). If B6 cannot say what the pattern is, the finding stands as NEEDS_REVIEW with B6's own reason (also listed under `needsReview`) — a question for a human, visible on the finding itself, not a coverage error.
- **excluded** — a valid non-candidate: an element that is not rendered, or a repeated block with no card surface (a layout column — nothing is painted to audit). Since engine r3 visible plain text (a caption, "Updated weekly", a stat such as "120+") is NOT an exclusion: it is audited as body text / a stat. Decided on the first read, never retried, never a corrective action, never an error. Listed in `excluded` (with its reason) for transparency only.
- **capture-failed** — a real candidate whose evidence could not be captured on either attempt (it changed or detached mid-capture). A true failure.
- **unresolved** — a reference that could not be read on either attempt (detached or replaced since the snapshot), or property coverage that would not stabilise. A true failure.

Only **capture-failed** and **unresolved** (`coverageErrors(report)`) reach `coverage.droppedRefs` — and so the "unresolvable element reference(s)" count in `report.html`, the Excel summary and the Figma "Coverage limits" card. An audit with nothing wrong has `droppedRefs: []`; plain captions and stat leaves never raise it. (Before Decision Log #40 every plain leaf B5 looked at was reported as "capture failed after 2 attempts": 26–28 bogus unresolvable refs on one real page.)

**After the cap, nothing is dropped — it is NEEDS_REVIEW.** An element B5 could not capture or resolve becomes a NEEDS_REVIEW finding (its accessibility-tree line is the evidence, its reason says how many attempts were made) and also stays in `coverage.droppedRefs`, the explicit counted list; a finding whose family search or property coverage will not settle within the cap keeps everything measured and gains the review (`markNeedsReview`; a measured breach keeps its classification, a clean or unverified result becomes NEEDS_REVIEW). `report.markedNeedsReview` lists them. The accounting invariant `unaccountedElements(output, report)` — every candidate-shaped element is a component, decided by B2, excluded with a reason, or a reported failure — is empty once verification has run.

**R1.2, extended, not invented.** RULES.md's own "WHEN NOT" for R1.2 names it directly: "`--brand-red` is button `variant=\"brand\"` ONLY … NEVER for borders · icons · section bgs · decoration · body text · headings · hover states." Only the heading-text half of that was measured before; B4's foundation check (run for every matched component, and re-verified by B5) now also measures `border-top-color` and `background-color` against brand red for any NON-button component (conservative: `button` is skipped entirely, since foundation-rules has no per-variant granularity to tell a real brand CTA from any other button) — this is the SAME rule's existing, explicit, measurable scope, not a new one invented for one page. It is a **prohibition, not a scale**: where B3 matched an element only by family identity (it does not conform to the variant — a badge with red decoration is still a Badge), the matched variant's own value for that colour can neither excuse the red nor replace its severity, so R1.2's citation stands next to the variant's mismatch rows (`filterFoundationViolations`, `keepProhibitions`); for an element that conforms to its component (class fingerprint, confident rule fit) the component's contract still decides. Scale rules (R1.3 / R3.5 / R3.6) always defer to the matched variant's exact value — which is why a 6px badge radius is reported as `6px → --radius-button (5px)` against the Badge, not as a separate R3.6 line.

**The hard cap: never more than `MAX_CORRECTIVE_LOOPS` (2) attempts per item, then a recorded outcome with the reason, never a silent guess, never a third attempt.** Every loop above (recovery-capture retry, property recheck, B3 re-ask) carries its own counter against this constant, and the verification passes themselves are capped at the same number: pass 1 verifies everything, pass 2 runs only if pass 1 corrected something and then only over what it touched, and a pass that corrects nothing ends the loop. A read that returns nothing is retried once; an `excluded` verdict is final on the first read. A page with nothing to recover or correct makes zero corrective actions and never touches anything beyond reading what is already there.

**Scope:** no-api mode only (the default and the only enabled mode — Decision Log #31), for the same reason foundation rules themselves are no-api-only today (`deterministicEvaluations` calls `checkFoundationRules`; `modelEvaluations` does not) — this is not a separate restriction B5 invented. ## Design System first, approved Project Aura reference second (locked — every future audit; engine r5, Decision Log #46)

**Matching priority — one fixed order, never re-derived per page:**

1. **Exact DS component / pattern** — the element IS an existing component/variant (B3 identity before compliance).
2. **Closest valid DS family / variant** — the family fits, the exact variant is uncertain or the styling is wrong: the family is kept and the closest valid variant audited; the differences are B4 findings.
3. **Approved Project Aura reference pattern** — supporting evidence, used ONLY when steps 1–2 found no clear DS representation (below).
4. **`NEEDS_REVIEW`** — still ambiguous: a human decides, with the evidence beside the question.
5. **B6, only for a genuine no-family / no-pattern** — an element no DS family represents AND no approved page uses as a consistent pattern.

**Never:** pick the nearest `SectionHeading` size before the element's semantic role is correct (role first, then DS matching) · treat an existing pattern with wrong styling as a new component · treat an uncertain variant as automatically new · let an HTML tag alone define identity (`h2`/`h3` ≠ `SectionHeading`; a `<p>` can be the main heading; a small text is not automatically a supporting heading) · force an ambiguous element into `SectionHeading` or any unrelated component.

**The reference evidence** is `reference/approved-reference-patterns.json` (loaded once per run by `loadReferenceCatalog`, `src/ds/reference-patterns.ts`; `referencePatternsPath` in the config overrides the location; a missing file is simply no evidence, a file that exists but cannot be parsed is a hard error). It records how the SAME semantic role (eyebrow on a light / dark surface, description under a heading, …) is really styled on each approved page — Report Store (`report-store-legacy`), Case Study (`case-study-v2`), Competition Benchmarking (`competition-benchmarking-v2-react`, the page the design lead confirmed as approved on 2026-10-07 — served at `http://localhost:3095`; `competition-benchmarking-v3` is NOT used) — as measured properties (font-size, weight, line-height, letter-spacing, text-transform, colour, family), each with the `file:line` it was resolved from (the Competition Benchmarking values were also checked against the rendered page's computed styles; nothing invented). Its `version` is a content hash and the file is fingerprinted by the engine guard, so changing one observed value is an engine change (bump the revision — see below).

**What an assessment can say (`assessReference`) — a verdict, never a decision:**
- **consistent** — at least two approved pages, no property they define disagreeing (lengths within a sub-pixel tolerance, a colour is the same painted colour) and at least three properties agreed.
- **single-source** — one page: not a pattern.
- **divergent** — the pages disagree; their own values are listed property by property, nothing is averaged or picked. (Today's real catalog: the eyebrow is **divergent** across the three pages — size 12 / 12.8 / 12px, weight 400 / 400 / 600, tracking 1.8 / 1.57 / 2.4px, and the Report Store's colour neutral where the other two are Ken red; only `text-transform: uppercase` and the DM Sans family are shared. The description under a heading is divergent too: weight 400 everywhere, but 14 / 14 / 16px, and line-height and colour differ. That is exactly why the audit does not pretend one "approved eyebrow" exists.)
- no evidence for the role → nothing changes at all.

**Where it is consulted — and where it never is.** B3's `attachReference` runs only when the DS search is **undecided** for the element's role (`decide(...)` returned no component and recorded why). A DS answer — an eyebrow matched to OverheadText / SectionLabel, a heading to SectionHeading, body copy / a stat numeral governed by the foundation rules — is never second-guessed by the catalog, which is not even read. When it is: **consistent** → B6 records a `DS_CANDIDATE` worded as a *reference-backed pattern proposed for Design System governance* (not a violation, not a new component); **single-source / divergent** → `NEEDS_REVIEW`, with the approved pages' own values listed beside what was measured; **no evidence for the role** → B6 decides exactly as it always did (a lone, unrepeated element is a question for a human). Either way the element is never forced into a DS component and the catalog is never a compliance target by itself — no finding is "wrong" only because it differs from a reference pattern.

Regression coverage: `test/unit/reference-patterns.test.ts` (the shipped catalog's real measurements and verdicts, the three verdicts, surface selection, loading and its failure modes, the content hash) and `test/unit/b3-reference-fallback.test.ts` (the DS is searched first and the catalog never read when the DS answered; a role with no DS family is consulted and attached as a verdict; consistent → reference-backed `DS_CANDIDATE`, divergent / single-source → `NEEDS_REVIEW`, no evidence → B6 exactly as before).

## B7 — Final Audit Coverage & QA (locked — every future audit; engine r5, recovery loop r7, Decision Log #45 / #47)

**The last node of the page graph: `B1 → B2 → B3 → B4 → B5 → B6 → B7`.** One independent job: verify that nothing meaningful on the rendered page silently disappeared from the audit. **100% accounting — not a claim of 100% correctness.** No existing agent was rewritten and no earlier edge changed: B7 calls B2's classifier and capture, B3's matcher, B4's evaluation and B6's evaluation in-process through the same functions B5 uses (one shared set of routing helpers in `src/agents/b5-visual-verifier/completeness.ts`; nothing is re-implemented). It is deterministic in every AI mode (`executionTypes.B7 = 'deterministic'`); in `anthropic-api` mode it accounts and marks gaps `NEEDS_REVIEW` but runs no corrective stage and does not judge roles with the deterministic classifier (`checkRoles: false`).

**B7 is a RECOVERY LOOP, never just a report of what is unaccounted (engine r7, Decision Log #47) — the same for single-page, full-site and re-audits, with nothing for the user to request:**

```
B1 → B2 → B3 → B4 → B5 → B6 → B7 ┐
                                 │  unaccounted > 0 ?
        send ONLY those items back through the stage that owns each of them
        (missed element → B2 → B3 → B4/B6 · wrong role → B2/B3 · missing DS match → B3 · missed property → B4 ·
         no DS family → B6 · hidden / hover / dropdown / carousel / accordion → reveal, then the normal flow)
                                 │  re-audit them with the SAME B2/B3/B4/B6 logic as the first audit
                                 │  REBUILD the Coverage Manifest, reconcile it, run B7 again
                                 └→ …until unaccounted = 0   (MATCH is an audited result — it is never unaccounted)
```

It always ends: an item gets **two attempts** and is then settled into one explicit, reasoned state (`EXCLUDED_WITH_REASON` — intentionally non-auditable · `CAPTURE_FAILED` — technically impossible to capture · `NEEDS_REVIEW` — unresolved, e.g. a hidden layer nothing safe opens); a round that changes nothing, twice, means no further round could either (**convergence**); and count / time / capture limits stop a pathological page. **The Coverage Gate passes only when `unaccounted = 0`.** Details: "The recovery loop" below.

**1. The Coverage Manifest — built independently, never from B2's candidate list** (`src/agents/b7-coverage-qa/manifest.ts`, `buildCoverageManifest`). A fresh in-page scan of the rendered page (scroll and any scrolled container reset first, so boxes match the snapshot): every visible text unit (block text and inline runs), heading, control, form field, badge/chip/pill-shaped leaf, surfaced repeated card and clickable card, plus content that exists in the DOM but is not painted by default — collapsed behind a `<details>`, tab, accordion or carousel, or a faded hover / scroll-in layer — each with its tag, role, text, box, computed style facts, section, and the control that reveals it. It is topped up with items only the accessibility tree lists and with any audited component the scan did not classify (so the manifest is never smaller than what was audited). Every item is stamped (`data-audit-b7`) so the audit trace can be read back from the page itself (`data-audit-el` stamps — an element's own stamp, an inner stamp covering ≥ 60% of its text, or an owning control/heading's; a card or section around words never covers them). Sources are recorded in the ledger: `dom`, `accessibility-tree`, `visible-text`, `computed-style`, `geometry`, `state-probes`. A page with ZERO B2 output still yields the full manifest (regression: `test/integration/b7-coverage-qa.test.ts`).

**2. Every discovered item ends in exactly one state — nothing is silently unaccounted:**

| State | Meaning |
|---|---|
| `AUDITED` | a component/finding exists for it (by the stamp, or by an owning heading/control covering its words) |
| `EXCLUDED_WITH_REASON` | an intentional exclusion, with the reason in plain words — B2's recorded decisions (sampled "N of M" listing, off-domain utility link, merged into another control, not rendered, visually hidden, not a candidate), B5's recorded exclusions, a personalised section, or a composite the classifier declines |
| `NEEDS_REVIEW` | a human must decide: a finding that says so, an `UNVERIFIED` one, or a gap B7 could not close within 2 attempts (settled in the Coverage ledger with its reason) |
| `CAPTURE_FAILED` | a real item whose evidence could not be captured (also added to `coverage.droppedRefs`, node `B7`) |
| *(UNACCOUNTED)* | the gap state — never a valid final state. Anything still in it is exactly what makes the gate fail |

**3. Gap routing — each gap goes to the stage that OWNS it, then returns to B7** (`src/agents/b7-coverage-qa/correct.ts`; no per-page or per-tag branch):

| Gap | Routed to |
|---|---|
| element missing from the audit | **B2** classify + capture → **B3** family search → **B4** audit / **B6** evaluate |
| wrong semantic / text role (eyebrow audited as `SectionHeading`; main heading audited as body text) | **B2 → B3** (re-classified, re-matched, re-audited) |
| wrong DS family / variant | **B3** (re-asked, bounded) → **B4** |
| missed property / compliance (radius, colour, gradient, spacing …) | **B4** — recomputed from a FRESH style reading (`extractComputedStyles`, the same reading B2 takes), the finding rebuilt by B4's own `buildFinding` |
| no existing DS family | **B6** (`evaluateUnmatched`) — and only then |
| content only an interaction reveals (hover layer, scroll-in, tab / accordion panel, carousel slide) | a **targeted state pass** (`states.ts`), **one reveal per hidden LAYER** — every member of a menu / panel is captured while it is open, so a layer nothing opens costs one failed attempt, not one per item: scroll into view → hover the layer's trigger, a control inside it, its parent (only where a pointer would really land) → keyboard focus → open the disclosure / tab and restore the originally selected tab → advance ITS OWN carousel's "next" control up to 8 times; captured while revealed (`captureState`), then the normal flow. **Every click goes through the audit's one safety predicate** (`src/t-layer/disclosure.ts`, the same one B1's expansion uses): never a link to another page, a form step that submits or collects personal data, a download or a new window, and a click that navigates anyway is undone — an unsafe control is reported as the reason, not operated |

**The recovery loop — how it runs and how it ends** (`src/agents/b7-coverage-qa/index.ts` `runCoverageQa`, `correct.ts`):

1. **Round.** Every gap — and only those items — is sent to the stage that owns it. Cheap, deterministic recoveries run first (a missing element needs a capture and nothing else); content only an interaction reveals runs second, a layer at a time, so an expensive reveal can never starve the rest (the real Customer Satisfaction Survey audit lost its whole budget to 24 failed hover attempts and never reached 48 plain items). Family and property verification covers every finding once (round 1), then only what a round touched.
2. **Re-audit and recheck.** Recovered items go through B2 → B3 → B4 | B6 with the first pass's own functions — **no new rule, no duplicate finding**: a recovered finding replaces the one it supersedes, an element the audit already holds is never captured again, and an audited element whose DOM stamp the page erased is still accounted for by its words and place (`linkTwins` — a `MATCH` included; the real audit reported six `MATCH` items as unaccounted before this). The manifest is **rebuilt and reconciled after every round**.
3. **Attempts.** An item gets at most **2 attempts** (`B7_MAX_PASSES` = `MAX_CORRECTIVE_LOOPS`), spent only when B7 actually examined it — an item skipped because a round ran out of room has spent none and is carried to the next round.
4. **Convergence — it never loops forever.** The loop ends when (a) nothing is unaccounted — *complete*; (b) every gap has spent its attempts, or a round examined nothing and changed nothing, or two rounds in a row left the gaps exactly as they were — *converged*: no further round could change the outcome; or (c) a safety limit is hit — *limit*: at most `B7_MAX_ROUNDS` (12) rounds, `B7_MAX_RECOVERIES` (2,000) captures and `B7_TIME_BUDGET_MS` (15 min) per page, and each round has its own slice (`B7_ROUND_RECOVERIES` 250 / `B7_ROUND_TIME_MS` 240 s) so progress is reconciled regularly.
5. **Settlement — nothing is left reading as "unaccounted".** What is still open after convergence (or whose attempts are spent) is settled into an explicit state **with its reason**: `NEEDS_REVIEW` for an unresolved case (a role that still disagrees, a captured element no stage could evaluate, a hidden layer nothing safe opens) — the existing finding, when there is one, is marked for review; an item that was never captured has no finding to mark, so its state lives in the **Coverage ledger** (no stub findings: hundreds of "nothing revealed it" rows would bury the real findings and bloat Excel / Figma); `CAPTURE_FAILED` for a technical capture failure twice in a row; `EXCLUDED_WITH_REASON` for something intentionally non-auditable (B2's classifier declined it, a sampled listing member, a visually hidden item, a personalised section).
6. **The only way to stay unaccounted** is the safety limit: an item B7 never got to examine because the loop hit its ceiling is **not** settled — running out of room says nothing about the item — it stays `UNACCOUNTED`, the gate **fails**, the report says `INCOMPLETE · N discovered · R remaining`, and the CLI exits 3. (A page with more items than the 8,000-item manifest also cannot pass: what was never enumerated cannot be accounted for.)
7. **Live state.** While a page is being re-checked the CLI prints `Coverage: RECHECKING · 473 discovered · 227 remaining`, once per round whose remaining count changed; a finished report is `PASSED` or `INCOMPLETE` — never "rechecking".

**4. The role check — classification validated, not trusted** (the locked heading-role rule, "Heading role before nearest-size matching"). B7 re-derives each text item's role (`eyebrow` · `main-heading` · `heading` · `description` · `paragraph` · `stat` · `label`) with B2's OWN classifier (`buildTypeContext` / `selectCandidates` / `classifyCandidateOutcome`) over the COMPLETE section hierarchy — position and order, relative size, weight, literal or CSS upper-case, tracking, colour, spacing, the dominant text, repeated patterns — and compares (component type, heading role) with what was audited. A disagreement is a role-classification inconsistency routed to B2/B3. It catches: `ABOUT KEN SURVEY` audited as `SectionHeading` while a larger dominant heading exists · a main heading implemented as a `<p>` that was never audited as a heading · a supporting heading in the wrong family · stat text audited as body copy or not at all.

**5. The Coverage Gate.** Final output per page and across the run: `discovered · audited · excluded (with reasons) · needs review · capture failed · unaccounted`. **`passed ⇔ unaccounted = 0`.** Above 0 the audit is marked **INCOMPLETE** and shows exactly which items are missing, where, and why. `needs review` and `capture failed` are accounted-for (a person sees them), they do not fail the gate. Across pages the gate passes only if EVERY page carries a ledger and none has anything unaccounted — a page with no ledger (reused from a run that predates B7) is never claimed accounted for.
- **Surfaces:** `data.json` (`coverage[].ledger` per page — the gate, the per-kind counts, every exclusion grouped by its stated reason (count + examples), **every** needs-review / capture-failed / unaccounted item in full (kind, text, section, box, reason), the corrective actions, the role-check tally, the sources and the manifest's stated boundaries; audited items are counted, not listed one by one; `pageSummary[].coverageGate`; `coverageSummary.gate`), `coverage[].ledger.recovery` — the loop's own account: recovery passes, items found / recovered / settled / remaining and why it stopped), the HTML report / dashboard (**v13: one compact Summary line `Coverage: PASSED · 473 discovered · 473 accounted · 0 unaccounted` — or `INCOMPLETE · 473 discovered · 227 remaining` — and everything else in a collapsed `Coverage details` accordion**), the Figma Overview tile (v6, unchanged), the Excel summary row, and the CLI: `Coverage: RECHECKING · N discovered · R remaining` while B7 re-checks, then `Coverage gate: <PASSED | INCOMPLETE …>` after every audit; an INCOMPLETE gate also prints `AUDIT INCOMPLETE — …` with the missing items to stderr and sets **exit code 3**.
- **Persistence & reuse (§4.4):** the ledger is stored per page (`coverage_ledgers`, migration 0007). A full-site run reuses a page only when its previous ledger exists AND its gate passed — and then carries the ledger; a reused page can never launder an incomplete audit into a pass.

**6. Stated limits (state them, never hide them):** content inside iframes is not scanned (counted in the ledger notes); `display: none` content that no control reveals cannot be discovered by a DOM scan and is not counted; content that is not in the DOM at all (lazily mounted and never triggered) is invisible to every DOM-based check; the manifest is capped at 8,000 items (`MANIFEST_MAX_ITEMS` — a truncation is stated and the gate then cannot pass on silence); the reveal pass tries the interactions above and nothing else — each one through the safety predicate, so a control that could submit, download or navigate is refused with its reason, and a hidden layer only a click (or a safe interaction B7 does not have) opens is settled `NEEDS_REVIEW` in the ledger after two attempts — one attempt per layer per round, never one per member; a carousel is left on the slide it was advanced to (tabs are put back; the page is a throwaway browser context, nothing persists); in `anthropic-api` mode B7 accounts but does not correct. A pass here means "every item the audit could discover is accounted for", never "every discovered item is correct".

Regression coverage: `test/unit/b7-ledger.test.ts` (the gate passes only at unaccounted = 0, one unaccounted item fails it, the numbers add up, every exclusion carries a reason, the cross-page gate), `test/unit/b7-reconcile.test.ts` (where each item is accounted — stamp, B2 decisions, B5 report, B7's settled decisions, policy exclusions; non-painted content is a state gap, never an exclusion; the role check for a supporting heading, a `<p>` main heading, literal upper-case, a description, stat text; **an audited element whose stamp is gone is still AUDITED — a `MATCH` included — one-to-one, never by words alone**), `test/unit/b7-outputs.test.ts` (data.json, the **compact HTML Summary line and the collapsed `Coverage details` accordion — including a 227-item unaccounted list that leaves the Summary one short line**, the Excel row, the Figma tile and colour, the CLI wording, template stamps), `test/integration/b7-coverage-qa.test.ts` (the whole graph through a real browser and the real Design System: independent manifest; `ABOUT KEN SURVEY` an eyebrow in Ken red; a `<p>` main heading, a mis-roled eyebrow and a mis-roled dominant `<p>` caught and corrected; stat text, a missing badge / card, a missed radius / colour / gradient recovered; hover layer, tab panel and carousel slide revealed and the page restored; every exclusion recorded with its reason; the gate failing at the safety limit and passing with it; reuse carries the ledger; **the recovery loop — ten gaps recovered across four rounds with the manifest rebuilt each time and no duplicate finding, a capture that fails twice settled CAPTURE_FAILED, a six-link hover menu revealed ONCE and every link audited, a click-only menu that cannot starve cheap recoveries and is settled once per layer per round, an erased stamp never re-audited**; each defect of the real run was mutation-checked — re-introducing it fails the matching test).

## Recovered-item section ownership & canonical element identity (locked — every future audit; engine r8, Decision Log #48)

Two rules for everything B7 recovers or reveals — the same for single-page, full-site and re-audit runs, nothing for the user to request. They live in `src/agents/b7-coverage-qa/ownership.ts` and `identity.ts`; no B1–B6 behaviour, DS rule, severity, confidence, heading role, report structure, Figma, Excel, Fix Plan or New Component Plan changed.

**1. A recovered item keeps its TRUE owning section — decided from the page's structure, never from where its box sits when it is read.** A mega-menu revealed from a sticky / fixed header has a page-absolute box that is the viewport position plus the scroll offset, so it lies over the hero (or whatever is scrolled under it); a y-range lookup filed "All Reports" and "SURVEY VERTICALS" under the hero's heading. `resolveOwner` is the one decision, first answer wins:

1. the section the audit ALREADY holds the element in (its component's own section — B1's ownership, preserved);
2. the section B1 adopted it into by DOM ancestry (`adoptedRefs`);
3. the nearest stable DOM section owner — the B1 section root whose SUBTREE holds it (B7 stamps every section root in the DOM, `data-audit-section`, before each manifest scan);
4. the owner of the control that reveals it (a hover host, a disclosure / tab control, an `aria-controls` trigger) — an overlay rendered outside its owner's subtree stays with the control that opens it;
5. a known structural region it sits in — Header / Navigation / Footer — resolved to that region's section;
6. geometry — ONLY for an item in the normal flow (never a fixed / sticky box, a dialog, or content that exists only while something is hovered / expanded), and only when B1's roots could not be anchored at all (the legacy rule, kept as the last resort);
7. otherwise NO owner: `(outside any section)`, and the finding written for it is marked for review ("nothing in the page's structure names the section it belongs to") — a measured breach keeps its classification. An unknown detached overlay is never assigned to the nearest visible section.

The owner is **revalidated from the live element right before a recovered finding is written** (`revalidateOwner`, `readLiveOwner`), and the ledger's action log says which basis decided it (`dom-subtree` · `trigger` · `region` · `component` · `adopted` · `geometry` · `unowned-overlay`). Header / mega-menu / dropdown content stays under Header / Navigation even over the hero; carousel and tab content stays in its parent section; a footer drawer stays in Footer.

**2. One physical element, one finding.** A finding id hashes the fingerprint (DOM path, role, name, text — the box is left out), so an element B7's recovery captured AGAIN (its stamp lost, or the layout moved it past the twin lookup's box tolerance) read as a fingerprint COLLISION and received a numbered second id: "How We Capture Dealer Needs" twice in one section. Identity is now combined evidence — **canonical DOM path + DOM role + normalised words + section**, with geometry and liveness to tell genuine look-alikes apart:

- `linkTwins` has a third tier: an element the page moved or re-rendered is found by that identity (so it is never "missing", never recaptured);
- before a recovered finding is kept, `reconcileCanonical` reconciles it against the findings the audit already holds (recovery: a re-discovered element may carry a different section label than the first pass gave it);
- **a final validation before the report is generated** merges any two findings of one canonical element + role + SECTION, in every audit mode;
- the merge is deterministic: the surviving finding keeps the EARLIER id, location and history; the classification is the strongest VALID one (a decisive result beats NEEDS_REVIEW / UNVERIFIED; INCORRECT > DEVIATION > candidates > MATCH; between equals the later reading); every property comparison, mismatch, rule violation and piece of evidence either reading found is kept; B7's records and the page's stamp are re-pointed at the survivor and the merge is logged ("merged into it, not audited a second time").
- what never merges: the same words in different sections; repeated list items (different DOM nodes — different `nth-of-type` paths); look-alikes sharing a path (shadow roots) that are both on the page, apart — the earlier element is still live, so the later capture is a different element, not a rediscovery.

Regression coverage: `test/unit/b7-section-ownership.test.ts` (header mega-menu over the hero · dropdown while scrolled · carousel / tab content · footer drawer · unknown detached overlay · the priority order), `test/unit/b7-canonical-identity.test.ts` (same heading recovered twice · same control in first pass and recovery · status change after recovery updates · same words in different sections · repeated list items · shadow look-alikes · the moved-element twin tier) and `test/integration/b7-ownership-identity.test.ts` (real Chromium: a sticky header's mega-menu over a hero is the Header's; stamps erased + layout shifted 300px leaves every finding id intact; the final validation merges an injected duplicate and leaves a genuine look-alike alone). Each rule was mutation-checked — re-introducing the geometry-only lookup or removing the canonical identity fails the matching tests.

## Global chrome first — structural regions & the Global Header sub-groups (locked — every future audit; engine r9, Decision Log #49)

**Global chrome is identified BEFORE the page's own sections.** B7 resolves every item to one of three structural regions — **Global Header · Page Content · Global Footer** — with no new agent, node or edge (`src/agents/b7-coverage-qa/ownership.ts`, `regions.ts`; the same for single-page, full-site and re-audit runs). No B1–B6 behaviour, DS matching, severity, confidence or heading-role logic changed.

**Ownership order (`resolveOwner`; supersedes the order in the r8 section above wherever they differ):**
0. **The landmark decides first.** An element inside the page's own banner (a TOP-LEVEL `<header>` / `role=banner`) or contentinfo (`<footer>`), **or revealed by a control that is** (a menu panel portalled outside the header, an `aria-controls` target), belongs to the Global Header / Global Footer section — whatever B1's section stamp or the first pass says. A `<header>`/`<footer>` of an article, section, main, nav or aside is NOT a page landmark (it is just that section's own heading block).
1. A **detached overlay** — fixed / sticky or a dialog, outside every section's subtree, opened by no section's control, in no header / footer — has no owner: `(outside any section)` and marked for review, **even when the first pass had filed it under a section by position**. Never guessed into the hero.
2. the section the audit already holds the element in · 3. the section B1 adopted it into · 4. the B1 section root whose DOM subtree holds it (roots are stamped `data-audit-section`; a page whose roots were only partly located falls back to geometry) · 5. the owner of the control that reveals it · 6. a loose region (header / navigation / footer) · 7. geometry — **only for normal-flow content**; never for a fixed / sticky box, a dialog or content that exists only while something is hovered / expanded.
- Dynamic content keeps the owner of its trigger: a header dropdown → Global Header, a hero carousel → Hero, a section accordion → its parent section, a footer drawer → Global Footer.
- A first-pass finding the landmark rule says belongs to the header / footer is **moved** there (`rehomeToRegions`; logged in the ledger); the Hero keeps only its own.

**Region and group are data, not names.** Every section gets `region` (`global-header` · `page-content` · `global-footer`) and every finding `location.region`; a Global Header finding also gets `location.group`: **`Base Navigation`** (the logo, the visible links, the menu triggers themselves) · **`<Trigger label> Menu`** — one per menu, named by the control that opens it (`Reports Menu`, `Industries Menu`, `Surveys Menu`, `Capabilities Menu`, `Insights Menu` …) · **`Search`** · **`Account/User Menu`**. Order in a report: base navigation, the menus in the order found, search, account / user menu. `location.section` still carries B1's own name (`Header`, `Footer`) — Excel and the Figma plan (which selects Header / Footer findings by that name) are untouched; only the HTML report titles the groups `Global Header` / `Global Footer`.

**Full-site.** `location.region === 'global-header'` is the same key on every page: a page's header findings are never attributed to that page's hero, and page-specific hero findings stay separate from them. (Collapsing identical header findings across pages into one is not done by this rule.)

Regression coverage: `test/unit/b7-global-regions.test.ts` (mega-menu over the hero · Reports / Industries (scrolled) / Search / Account menus · base navigation · hero carousel · section accordion · a card `<header>` in an article · footer drawer · a detached overlay, first-pass and recovered · region / group annotation · the HTML grouping), `test/integration/b7-global-header.test.ts` (real Chromium, one page with all of it) and the earlier `b7-ownership-identity` / `b7-canonical-identity` tests (duplicate-finding prevention). Each rule was mutation-checked.

## Role-first typography & the DS type scale (locked — every future audit; engine r10, Decision Log #51)

**The order is fixed: identify the element's ROLE → select the DS rule or component that role names → compare its typography against THAT.** Neither the HTML tag nor the font size alone decides a role. Same code for single-page, full-site and re-audit runs.

**1. R1.3's accepted sizes are the DS's own scale — not "any token that looks like a text size".** The DS rule (RULES.md R1.3) says: scale **12.8 / 16 / 20 / 25 / 31.25 / 39 / 48.8 / 61 / 76.3**, "only deviate for spatial constraints (use --text-compact 14 · --text-nav 14 · --text-2xs 11 · --text-card-micro 10)". Text-size tokens are now **classified** (`classifyTextTokens`, `foundation-rules.ts`), and only the first two classes are valid sizes for general text:
- **scale** — the general typography tokens, the Major Third steps (`--text-xs … --text-5xl`);
- **documented exception** — the sizes R1.3's own "WHEN NOT" names, read from the DS rule text (the four above when the rules are unavailable);
- **legacy remap** — kept for old pages, listed under "ADDED TYPE TOKENS · V0.2 remap" in the DS base styles, never part of the scale: `--text-md` (18), `--text-13`, `--text-24`, `--text-30`, `--text-32`, `--text-48`, `--text-nav-helper`;
- **component-specific** — owned by one component (`--button-font-*`, `--badge-*-font`, `--text-paywall-*`, `--text-data-label`, `--text-eyebrow`, `--text-source-citation` …): the matched variant's own contract governs them, they never widen the general scale;
- **alias** — a second spelling (`--typography-size-*`, `--font-size`) never trusted over the `--text-*` token it mirrors (`--typography-size-2xs` is 11px in FOUNDATIONS but a 12px CSS fallback in `utilities.css`, whose own note says "Never use text-2xs for body or UI labels").
So 18px, 13px-class legacy sizes, 24 / 30 / 32px and **12px** are off the scale (nearest valid step, ties → the larger), and the R1.3 finding names the legacy / component token the size equals. Verified against the DS source before the 12px question was decided: 12px is not an intended DS size.

**2. Roles B2 decides from the section (B7's independent role check reads the same).** On top of `eyebrow` / `main` / `description`:
- **`card-title`** — a title over a smaller description whose pattern REPEATS across the section's cards (read from geometry: the smaller text directly beneath it; ≥ 2 alike), 16–26px, ≤ 12 words, and heavier than body copy or heading-tagged — never the tag alone (a card title is often a `<p>`), never the size alone. It is judged by the **DS card-title contract** (R4.3.5 + R1.4 "H4 card titles"): `--text-base` 20px with 4+ cards or `--text-lg` 25px with 2–3, **DM Sans 500** — e.g. an 18px/500 card title → **20px**.
- **`label`** — a SHORT (≤ 6 words) heading-tagged text whose size is **below the DS heading range** (H3 starts at 25px; H4 card titles are 20px), that is none of the roles above and has no structural doubt (clickable, in a footer / navigation, one of several identical blocks): an `h2` used as a diagram / UI label. It is typed `paragraph` and audited on the foundation rules like body text — **never forced into SectionHeading by its tag**; 16px DM Sans passes.
Both are typed `paragraph` with `headingRole`, so B3 answers foundation-only (never B6) and B4 applies the role's contract (`checkFoundationRules({ role })`).

**3. "Foundation checks passed" is not "a DS component matched".** A clean text element carries the additive `comparison.basis` — `foundation-only` (no component applies: body text, a card title, a label, supporting copy) or `ds-component`. For `foundation-only`: the recommendation says *"No foundation issues found — typeface (R1.4), size (R1.3), colour (R1.1 / R1.2) verified. No Design System component applies to …, so no component comparison was made; this is not a component match."*; the evidence line says *"Foundation checks only — 3 verified (font-family, font-size, color); no Design System component was matched or compared"*; and **the property table lists each verified property as a verified `MATCH` with the DS value it was verified against** (`verifiedTextRows`: e.g. `font-size 16px → 1rem (--text-sm)`) — never "Not verified" next to "3 passed". Properties nothing verified (line-height, width, …) stay `UNRESOLVED`, honestly. The HTML detail shows a **Match basis** cell (`html-report-v19`).

Regression coverage: `test/unit/b4-nearest-typography.test.ts` (the accepted scale, the token classes, 18 → 20, 12 → 12.8, the exceptions), `test/unit/b-text-roles-typography.test.ts` (the roles from geometry, tag-and-size together, the card-title contract, the verified rows), `test/integration/text-roles-typography.test.ts` (real Chromium: card titles, a label, 18px / 16px / 12px text, the wording, the table, B7 agreeing with B2) and the updated `b-deterministic` / `b-heading-roles` tests. Each rule was mutation-checked.


### FAQ questions and clickable labels (engine r11, Decision Log #52)

Two more roles, decided like the others — from role evidence together, never the tag, the size or the phrasing alone:

- **`question`** — a clickable heading (itself `[cursor=pointer]`, computed pointer, or inside a clickable) phrased as a question, ≥ 3 words, ≤ 18px (FAQ size — a 20px+ clickable title ending in "?" is an article / card title, engine r12), not in the footer / navigation. Judged against the DS **AccordionItem** question (`--text-sm` 16px, weight 500): accepted sizes are 16px AND the documented R1.3 compact-text exception (14px, `--text-compact` / `--text-nav`) — a 14px question PASSES; any other size gets ONE recommendation, the nearest accepted size (an 18px question → 16px; R1.3, "AccordionItem question is --text-sm") — never SectionHeading's 31.25px; a wrong weight is LOW R1.4. The generic R1.3 does not also fire.
- **`label` (clickable)** — a short (≤ 6 words) clickable heading ≤ 20.5px, such as an index / selector entry ("01 Employee Engagement"): audited on the foundation rules like body text (14px is a documented R1.3 exception), never SectionHeading.
- A clickable heading at display size, a heading in the footer / navigation and a repeated-unit title keep the LOW-confidence section-heading doubt path unchanged.
- Locked by `test/unit/b-text-roles-typography.test.ts` ("FAQ questions and clickable labels") and `test/integration/text-roles-typography.test.ts`.

## Engine revision & full-site reuse (Decision Log #39)

A full-site run **reuses** a page's previous findings when the DOM hash and the Design System registry version are unchanged AND every prior finding's `identity.policyVersion` equals the current one (the §4.4 memoization in `src/agents/page-graph.ts`). So `policyVersion` has to change whenever the audit's *behaviour* changes — otherwise a page audited before a B1/B2/B3/B4/B5 fix keeps its old, now-wrong or now-incomplete findings forever, merely because its DOM did not move.

- **What it is:** `policyVersion = <S8 policy tag>+recommendations-context-v2+engine-r<N>+ai-<mode>+browser-<channel>@<version>+playwright@<version>`, built in one place (`policyVersionFor`, `src/graph/run-metadata.ts`). `<N>` is `AUDIT_ENGINE_REVISION`.
- **When to bump it (and add a line to `ENGINE_REVISION_LOG`):** whenever a change alters what an audit REPORTS for the same page and Design System — which elements B1/B2 find, own or sample; which family B3 searches and how it picks a DS value; which rules B4 applies or what they say; what B5 recovers or counts; the recommendation wording. A pure refactor, a comment, a test or a doc needs no bump.
- **Effect:** findings an older engine produced are NOT reused — the page is audited again by the current engine (the full-site run's coverage then shows no `reused result` for it). When nothing changed — same DOM, same DS, same engine — reuse still works, so the memoization keeps its speed-up.
- **Re-audit:** the first re-audit after a bump states the change as an S7 baseline change ("audit policy / browser changed since run X"), and a finding is never called `REGRESSION` or `RESOLVED` on that basis alone (Decision Log #29). Runs already stored keep their old findings and old `policy_version` unchanged until the page is audited again.
- **Guard:** `test/unit/engine-revision.test.ts` pins a fingerprint of the sources listed in `ENGINE_SOURCE_FILES` — every file of a B1–B7 stage directory (the test fails if a new one is left off the list) plus the shared helpers that decide a value, its wording or what is accounted for (including the approved reference catalog, `reference/approved-reference-patterns.json` — its observed values change what an audit reports, so its content is fingerprinted too) — measured on their code tokens, so a comment, JSDoc or reformat does not trip it. Editing one fails the test, and its message names the changed files and prints the paste-ready pin, until the revision is consciously handled: if behaviour changed, bump `AUDIT_ENGINE_REVISION`, add its `ENGINE_REVISION_LOG` line, set `PINNED_REVISION` and re-pin; if it did not (a refactor, a rename), only re-pin. A new helper that decides what an audit reports belongs in `ENGINE_SOURCE_FILES`. Concurrent sessions editing these files will see the guard too — that is by design.
- **Regression coverage:** `test/unit/engine-revision.test.ts` (the policy string, the revision log, the fingerprint guard) and `test/integration/engine-policy-reuse.test.ts` (the real full-site graph: a control run reuses; the same page whose stored findings carry an older engine's policy is audited again; the re-audit says baseline change rather than regression).

## The nine-point contract for every `url` + `mode` + optional `run name` request

## Step 1 — Confirm the environment, don't assume it

Before running anything:
- `cd` into the audit-agent repo root (wherever it's checked out on this machine).
- Run `git status --short` — if there are uncommitted source changes, tell the user and ask whether to proceed; never audit against a dirty, unverified tree without saying so.
- Run `npx tsc --noEmit` — must be clean.
- **Silently probe the Figma MCP connector now, once (with retries), upfront** — a single bounded call (e.g. `whoami` on the Figma MCP tools), before anything else runs. Classify whatever comes back into exactly one of three recorded outcomes, then move straight on to Step 2 regardless — **do not pause, do not wait for a response, do not ask the user anything at this point**:
  1. **Authenticated** — record it (team/plan info included). Step 6 will publish automatically from this; no separate "publish to Figma" request is ever needed.
  2. **Transient/tool/session error** (timeout, connector hiccup, an MCP error that is not itself an auth/permission response) — retry the same probe automatically up to 2 more times (3 attempts total, no pause between them, no question to the user). If every attempt fails the same transient way, record "not available this run" — treated identically to never having connected at all. Never block waiting for a transient failure to clear on its own.
  3. **Explicit authentication/permission denial** — the connector itself returns something equivalent to `unauthorized`, `login required`, or `permission revoked` (a real denial, not a generic error) — record the exact signal, verbatim. - **Run ID**, compliance/finding counts (match/deviation/incorrect/needs review/unverified), coverage notes, and test-suite pass/fail
- **Template versions used** — `FIGMA_CONTRACT_VERSION` and `HTML_TEMPLATE_VERSION` (both inspectable in the outputs themselves: `figma-plan.json`'s `contractVersion`, `report.html`'s `<!-- html-report-v19 -->` comment) — so the user can see at a glance that this run used the locked template, not a redesign
- **Engine revision and reuse** — the `engine-r<N>` inside `data.json`'s `run.policyVersion`, and for a full-site run how many pages were reused from an earlier run (`coverageSummary.truncation` entries with `what: "reused result"`) versus audited fresh. A reused page is only ever one the current engine already audited with its DOM and the Design System unchanged (see "Engine revision & full-site reuse"); also state the coverage honestly — `coverage.droppedRefs` (true capture failures / unresolved references only) and `coverage.sampledListings` (what was sampled, as "N of M")

## Hard rules (do not relax these for convenience)

- **Never** redesign A1–A4/B1–B7, the graph, the database schema, or the output contract to make a specific page "work." If a page genuinely breaks the pipeline, that's a bug to report and fix in the underlying code/tests — not a one-off workaround for this run.
- **Never** let low compliance override a clear component-family identity — see "Component identity vs. compliance" above. A badly-implemented CTA is still that CTA family; B6 is for genuinely new patterns only, never a dumping ground for non-compliant existing ones.
- **Never** treat an `h1`/`h2`/`h3` as automatically a `SectionHeading`: classify the role from the section first (supporting heading/eyebrow · main heading · description) — see "Heading role before nearest-size matching". A supporting heading is Ken red on a light surface, the DS inverse treatment on a dark one; never force it into `SectionHeading`, and never apply the red rule to a small heading that is not a supporting heading.
- **Never** mark an audit complete, finished or "100%" while the Coverage Gate has `unaccounted > 0` or a page with no ledger — it is INCOMPLETE, and the missing items are listed. The gate is 100% accounting, not a claim of 100% correctness; never reword it into one.
- **Never** stop B7 at reporting what is unaccounted, build or repair its manifest from B2's candidate list, hand-edit a ledger, or close a gap by loosening the gate. While anything is unaccounted, exactly those items are sent back — through the stage that owns each (B2 · B3 · B4 · B6 · the layer reveal) with the same logic as the first audit — the manifest is rebuilt and B7 runs again, until `unaccounted = 0`. It ends by convergence (two attempts per item, then an explicit reasoned state: excluded · needs review · capture failed; a round that changes nothing, twice; the count / time / capture limits) — never guessed, never silently dropped, never an exclusion without a stated reason, never a duplicate finding, never a `MATCH` reported as unaccounted.
- **Never** assign a recovered or dynamic item (a mega-menu, a dropdown, a hover layer, a carousel / tab panel, a footer drawer) to a section from its box or the viewport position at the moment it was revealed — its owner is its section's DOM subtree, the control that opens it, or its Header / Footer region (see "Recovered-item section ownership & canonical element identity"). Header / mega-menu content never lands under the hero or a content section; an overlay no structure owns is `(outside any section)` with a review note, never the nearest visible section.
- **Findings are listed in reading order** inside each section (html-report-v19): top to bottom, left to right along one visual row, an enclosing card before its contents, from the page-absolute evidence box the audit already stored (`src/output/reading-order.ts`). `data.json` keeps the audit's detection order; only the report's list is ordered. Never hand-reorder findings for a page.
- **Never** change the Findings view's locked section spacing for a routine audit: **10px before each new section header** (never between finding rows, never before a sub-group header, never before the first section), **section headers 10px tall in padding, sub-group headers 8px**, and the Global Header / Global Footer accordion buttons share the same spacing. It lives in the one shared template (`src/dashboard/views/render.ts`, `html-report-v19`), so every future single-page, full-site and re-audit report — and the live dashboard — inherits it with no per-run step; `test/unit/b7-global-regions.test.ts` pins the exact CSS. Changing it is an explicit template change (bump `HTML_TEMPLATE_VERSION`, update that test and the docs).
- **Never** accept an off-scale text size because SOME DS token equals it, and never decide a role from the tag or the size alone: R1.3's valid sizes are the DS Major Third steps plus the exceptions R1.3 names; legacy remap tokens (`--text-md` 18, `--text-13/24/30/32`), component tokens (`--button-font-*`, `--badge-*-font`) and aliases (`--typography-size-*`) do not make a size valid for general text. A card title is judged by the card-title contract (20px / 25px, DM Sans 500), a short heading-tagged text below the DS heading range is a label (foundation rules), and neither is forced into SectionHeading by its tag. A clean text element says foundation checks passed — never "matches the Design System" — and the property table shows exactly what was verified (see "Role-first typography & the DS type scale").
- **Never** attribute header navigation, a menu / mega-menu, search, the account / user menu or any overlay opened from the header to the hero or any page-content section: the page's banner landmark (or the control that opens the overlay) makes it **Global Header**, with its sub-group (Base Navigation · `<Label> Menu` · Search · Account/User Menu); a footer drawer is **Global Footer**. A `<header>` inside an article or section is not the Global Header. Geometry never moves a header menu into the hero, and an unowned detached overlay is `(outside any section)` + review — never a guess (see "Global chrome first").
- **Never** write a second finding for an element the audit already holds: recovery reconciles every recovered finding against existing ones by canonical element identity (DOM path + role + words + section), merges the evidence into the earlier finding (same finding id), and a final dedupe validation runs before the report is generated. The same wording in different sections, different DOM nodes in a repeated list, and live look-alikes stay separate findings.
- **Never** let the approved Project Aura reference catalog replace the Design System or act as a compliance target: Design System first, reference second (only when the DS search was undecided), `NEEDS_REVIEW` third — and never force an ambiguous element into `SectionHeading` or any unrelated component to make it match.
- **Never** pick a Design System typography size or heading level from the element's semantic tag (h1/h2/h3). The size is the **nearest** DS size to what was rendered — see "Typography: the nearest Design System size" above — and a recommendation never asks to change an element's HTML level to adopt it.
- **Never** recommend a numeric DS value outside the "Nearest-match precedence" order: the exact value of the matched component variant first (a nearest-token search must never override it), otherwise the single nearest valid token of the property's OWN token family (never a numerically close token from an unrelated family, never the generic "use a DS token"), otherwise Not resolved / `UNVERIFIED` / `NEEDS_REVIEW` — never an invented value. It is one shared mechanism for single-page, full-site and re-audit runs; no per-page or per-property special case.
- **Never** change what B1–B7 detect, match, compare, account for or report without bumping `AUDIT_ENGINE_REVISION` and adding its `ENGINE_REVISION_LOG` line (`src/graph/run-metadata.ts`) — see "Engine revision & full-site reuse". Without the bump a full-site run keeps reusing the findings an older engine produced for any page whose DOM and DS did not change. `test/unit/engine-revision.test.ts` fails on an unacknowledged engine-source edit; re-pinning it is a deliberate act, never a way to make the suite green.
- **Never** count a valid exclusion as an error — an unrendered element, an off-domain utility link, a listing member sampled out on purpose, an element merged into another control. Only a candidate whose capture failed, or a reference that genuinely would not resolve, belongs in `coverage.droppedRefs` (B5 `coverageErrors`). Equally never hide a real failure: a true capture failure or unresolved reference is reported, never swallowed.
- **Never** send an element to B6 while an existing Design System family could represent it, and never call a recovered element, or an existing component with wrong styling, a new component. Identity (which family it is) is decided before compliance (how well it is styled); the wrong styling is a B4 deviation from that component. B6 is only for a pattern no family represents — and B5 re-verifies B3's family search before it lets one through.
- **Never** fix a missing element by widening a later stage. B1 owns which elements belong to a section (its y-range and its DOM subtree), B2 owns which are candidates and what is sampled, B5 only verifies and recovers what those two genuinely missed. A gap is fixed in the stage that owns it, once, generically — and it is never a reason to add an agent, a node or a graph edge.
- **Never** show an Expected typography value in `rem` without its resolved px in any report surface (HTML, dashboard, Figma plan, Excel, anything new) — route it through `expectedForDisplay` / `recommendationForDisplay` ("Report formatting rule") with the finding's page root (`pageRoots(data).of(finding)`) — never an assumed 16px. And never get there by changing a stored value: `data.json`, a finding's `expected`, a recommendation's text and a DS token are the audit's own and stay as produced.
- **Never** infer `mode` from the URL. Ask if it's not stated.
- **Never** call `figma-plan.json`/`figma-composite-plan.json`/`figma-ops.json` a completed Figma deliverable — they are the plan; Step 6's real publish + verification is the deliverable.
- **Never** let Figma's connector status turn into a pause or a question back to the user mid-run. It's probed exactly once, in Step 1 — with up to 2 automatic retries for a transient/tool/session error only, never for an explicit auth denial, and never anywhere later in the run — and every later step acts on whatever got recorded there. A never-connected or transient-failure-after-retries connector is a normal, non-blocking outcome. An explicit auth/permission-denial signal (`unauthorized`/`login required`/`permission revoked`/equivalent) is the one outcome that earns a distinct, stronger call-out in Step 8 — but even that is reported at the end, never asked mid-run; the run always completes regardless.
- **Never** require a separate "publish to Figma" request when the connector is authenticated — a real Figma publish is simply part of that run's normal output (Step 6), not an extra step the user has to ask for.
- **Never** hand-curate Figma marker content, positions, geometry, or root-cause grouping again — that logic lives in `src/figma/publish-plan.ts`/`page-composite-plan.ts`/`publish-ops.ts` now. If it looks wrong for a new page, that's a bug in that code (fix it and add a regression test), not something to patch by hand in the Figma file.
- **Never** silently skip a verification step in Step 5, or one of `publish-verify.ts`'s checks in Step 6, to save time — report what you didn't check rather than implying you did.
- **Never** redesign the Figma six-page structure/cards/colors or the HTML template's cards/palette/layout for a routine audit request — a new URL changes the data (findings, counts, screenshots, marker numbers), never the template. A template change happens only on an explicit user request, as one code+version-constant change in `publish-plan.ts`/`publish-ops.ts`/`render.ts` — never as an ad hoc per-run decision, and never by retyping content (e.g. the Legend's color-key line, `legendColorKeyLine()`) from memory instead of calling the function that generates it.
- **Never** let the HTML template's `STATUS_COLORS` drift from the Figma template's status-color meaning (Incorrect=Red, Deviation=Orange, Needs Review=Amber, Unverified=Gray, Match=Green) — this drifted once (Unverified silently reused the amber Needs-Review hue) and is now regression-tested (`test/unit/html-template-palette.test.ts`); don't reintroduce it.
- **Never** ask the user for a save path — output location is fully automatic (`audit-agent/projects/<project-slug>/runs/<run-id>/`, see "Project/output path & run naming" above). If a run somehow lands anywhere else, that's a bug in `DATA_ROOT`/`AUDIT_AGENT_DATA_DIR` resolution to report, not something to route around by asking the user where to save.
- **Never** let the run's display name collapse into its slug anywhere a human reads it (Figma file name, friendly report filenames, the confirm block) — that drifted once too (this exact gap is what `resolveRunName`/`run.json` exist to close); regression-tested in `test/unit/run-naming.test.ts`.
