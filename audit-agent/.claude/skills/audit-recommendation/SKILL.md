# Evidence-based audit recommendations

Read the configured project's actual DS sources. For Ken/Aura, use `core-v2` component JSX, approved recipes and `core-v2/docs/ICONS.md`; consult the project's `aura-design` for contextual design reasoning. Do not apply Ken-specific policies to another project without checking its sources. UI/UX Pro Max is advisory and must not override the configured DS; its current Aura wrapper is scoped to Loop review.

## Identify before comparing

- Determine purpose, parent composition, child slot, surface and observed interaction state before selecting a visually close variant. A breadcrumb child is not a standalone TextLink/CTA merely because it renders an anchor/button.
- Retrieve compatible components first. Compare their source-governed properties; preserve those already matching. Nearest means nearest among semantically compatible, state-compatible options, not nearest in the entire palette.
- Use ancestor surface evidence, not foreground colour, for dark/light. Image/gradient backgrounds require review when their effective surface is unresolved. Never infer active/hover/pressed from a colour match.
- A strong family identity survives poor styling. A generic element role alone does not prove a compound child is that family. Name ambiguity and do not present an uncertain candidate as a mandatory correction.
- Compound slots must use their own source styles. When a production control combines slots the parser cannot compare safely, explain the approved composition and missing evidence rather than prescribing a primary Button.

## Role before family (locked)

- **A text's role is decided from the section's whole hierarchy before any DS family is named** (audit-run, "Heading role before nearest-size matching"): supporting heading / eyebrow · main section heading · description. An `h2`/`h3` is never automatically a `SectionHeading`, a small text is never automatically a supporting heading, and a main heading can be a `<p>`. The recommendation for an eyebrow compares it with the DS eyebrow family (OverheadText / SectionLabel), never with `SectionHeading` sizing; the finding states the role it was classified as and why (the `heading role: …` evidence entry).
- **Supporting-heading colour:** Ken red on a neutral / light surface; on a dark or brand surface the DS inverse treatment applies (SectionLabel's own dark tokens) — red is never forced there, and never applied to a small heading that is not a supporting heading. Where the DS governs no `line-height` for the pattern, say "not governed — inherits" instead of inventing one.
- **Matching priority:** exact DS component/pattern → closest valid DS family/variant → approved Project Aura reference pattern (supporting evidence only, consulted only when the DS does not clearly define the role) → `NEEDS_REVIEW` → B6 only for a genuine no-family/no-pattern. When a recommendation rests on reference evidence, say so and show the approved pages' values — "reference-backed existing pattern, proposed for DS governance" for a consistent one, a question for a human for a divergent or single-source one; it is never presented as a Design System rule or a mandatory correction (audit-run, "Design System first, approved Project Aura reference second").
- **A recommendation exists only for an element the audit reached.** The Coverage Gate (B7) is what says whether anything on the page was left out; never write a "page is clean" conclusion while the gate is INCOMPLETE.

## Recommendations and gaps

Show current value, proposed value/token, DS file/variant, context and confidence. Keep measured violations separate from implementation advice. Missing measurements are unknown, not zero or proof of a mismatch.

**A proposed numeric value follows the locked precedence in audit-run ("Nearest-match precedence"), for every numeric property and not only font-size:** (1) the exact value of the matched component/variant — never overridden by a nearest-token search (`Button / primary / md / light` requires `radius: 5px` → 5px); otherwise (2) the single nearest valid token of the SAME token family (type size → type scale, padding/margin/gap → spacing scale, radius → radius scale, line-height → line-height tokens, letter-spacing → tracking tokens: `6px` radius → `5px`, `8px` → `8px`, `32px` heading → `31.25px`), with rem/em/px normalised to one unit before measuring, and stated as current value → nearest valid value (difference); otherwise (3) Not resolved / `UNVERIFIED` / `NEEDS_REVIEW` with the reason — never a generic "use a DS token", never a value from a numerically close but unrelated family, never an invention. The element's semantic identity (tag, role, component family) stays out of the choice and is never changed by it. Same rule for single-page, full-site and re-audit runs.

When no equivalent is verified: inspect parent composition and approved recipes, then propose reuse of approved atoms/tokens. Clearly label a new composition as a proposal and identify the evidence still needed. Never invent token names, glyphs or literal dimensions, or auto-approve a new DS component.

For image/SVG UI controls, check `allowedIconLibraries` in audit-agent.config.json before the DS default. The user's approved policy for this project permits **only Lucide React (`lucide-react`) or Phosphor (`@phosphor-icons/react`)**. This explicit override takes precedence over the DS document's older Lucide-only default; do not describe Phosphor as a DS violation. Preserve the existing allowed library and visual style when suitable. Do not suggest other libraries or arbitrary image substitutes for UI icons. Recommend an exact equivalent only after confirming the action/glyph meaning. An unlabelled control needs an accessible name and semantic verification. Exclude logos, photography, avatars and brand artwork. Do not infer React package provenance from a rendered SVG alone. Preserve valid measured findings when adding icon advice.

Persist measured properties separately from mismatches, including passing and unresolved properties. Expected values may be unknown while Actual remains readable; show `Not resolved` and a specific reason rather than blanking both. Compare SectionHeading's actual h1/h2/h3 child at the captured breakpoint, not the wrapper — and choose WHICH level by the nearest DS size to the rendered one, never by the element's tag: an h2 at 32px is compared with level 3 (31.25px / 1.953rem, 0.75px away), not level 2 (39.06px), and it stays an h2; state Actual, Closest DS value, Difference and DS source, and never recommend changing the HTML level to adopt a nearer visual size (see audit-run, "Typography: the nearest Design System size"). Treat long h2 copy below h1 as a possible subtitle, with candidate expectations clearly marked until its role is confirmed. For a combined breadcrumb dropdown, compare label typography separately and expose arrow/container observations without inheriting standalone CTA dimensions. Partial coverage cannot produce an unqualified MATCH.

Write the recommendation once in plain action-oriented language. Do not concatenate the review reason with an identical recommendation. Show full element labels in details. **Expected typography in `rem` is always displayed with its px** (`2.441rem (39.06px)`) in every report view — summary, property table, detail and recommendation alike — converted with the root font size MEASURED on that finding's page (`pageSummary[].rootFontSizePx`), never an assumed 16px. That is a display rule applied by the report layer (`expectedForDisplay` / `recommendationForDisplay`, `src/output/display-values.ts`; see audit-run, "Report formatting rule"): the stored recommendation text and expected value stay exactly as B4 wrote them, so quote an expected value in B4's one format `<property>: <actual> → <expected>` and never hand-append the px yourself. If component/policy baseline changed, distinguish the historical issue from the current unverified result; do not imply the old mapping is still a confirmed defect.

Section labels must describe the actual section, not a nested card title or price. Prefer explicit accessible labels and section-level titles; mark inferred text labels in evidence. Persist section IDs so duplicate names remain distinct. Filter options, group headings and findings must use the same section inventory; zero findings does not mean the section was absent.

## Runtime and verification

Markdown alone does not change CLI results. The runtime enforcement lives in `src/t-layer/dom-facts.ts`, `src/ds/context-models.ts`, B3/B4 matching, `src/skills/contextual-recommendations.ts`, section extraction and the shared report renderer. When changing these policies, bump `AUDIT_ENGINE_REVISION` (and add its `ENGINE_REVISION_LOG` line) in `src/graph/run-metadata.ts` — that is what keeps a full-site run from reusing findings, and recommendation wording, an older engine produced (`test/unit/engine-revision.test.ts` fails until you do; see audit-run, "Engine revision & full-site reuse") — and run the relevant regression tests.

Verify dark/light breadcrumbs, current/rest state, combined dropdowns, image controls versus brand images, unsupported sources, uncertain matches, duplicate/zero-finding section filters, and — for headings — the eyebrow / main heading / description roles on both a light and a dark surface. Re-audit into a new run after engine changes; historical findings remain historical. Report which outputs were actually regenerated.
