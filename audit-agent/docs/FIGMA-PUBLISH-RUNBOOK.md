# Figma Publish Runbook (Decision Log #32, codified — hover-visibility fix Decision Log #34 — component-library containment fix Decision Log #37)

**Audience:** a Claude Code session with live Figma MCP tool access (`use_figma`, `create_new_file`, `upload_assets`, `get_screenshot`, etc.) — never a bare CLI command, and never the headless Claude Code path (`src/figma/publish.ts`/`prompt-contract.ts`'s `buildPublishInstruction`, a different, confirmed-failed, LEGACY path — see those files' headers).

**Why this exists, and why it's short:** the interactive-marker Figma system (curated root-cause markers, hover annotation cards, sticky-header-safe full-page composites) was built and proven correct by hand against one real run (`market-entry-real-1`). Every rule discovered during that pass — dedup, tiling, marker Y-clamping, `clipsContent`, Legend+list placement, blank-image prevention — is now **code**, not prose:

- **What to build**: `src/figma/publish-plan.ts` (marker dedup, colors, content) + `src/figma/page-composite-plan.ts` (tiling geometry) → `figma-plan.json` / `figma-composite-plan.json`.
- **Exactly which operations to perform, in order, with every rule baked into the data**: `src/figma/publish-ops.ts` → `figma-ops.json`. `clipsContent: false` is a literal field on every marker component-set op, not a step to remember. Every image-upload op past the first tile is pre-cropped by the measured header height — a raw, uncropped tile can never be emitted. Every marker's placed Y is pre-clamped ≥ 0. The Legend panel and its numbered list are the SAME operation, so they cannot land after the Footer or as a detached panel.
- **What to verify, against what actually came back**: `src/figma/publish-verify.ts` — `checkBlankImage`, `checkHoverCardNotClipped`, `checkBounds`, `checkMarkerTraceability`, `checkLegendPlacement`, `checkNoMatchMarkers`, `checkComponentLibraryVisible`, `checkMasterParentedInLibrarySection`, `checkNoMasterOverlap`, `checkLibrarySectionContainsAllMasters` (Decision Log #37 — the live containment checks; `checkComponentLibraryHidden` above is the OLD, disproven name, kept only as a reminder not to reintroduce it — see Decision Log #34).

This runbook is now just the **mechanical replay procedure** over `figma-ops.json` — there is no remaining judgment call about which findings matter, where a marker goes, what a card says, or how to crop a tile. If something looks wrong, it's a bug in `publish-ops.ts`/`publish-plan.ts`/`page-composite-plan.ts` (fix it there, add a regression test to `test/unit/figma-publish-ops.test.ts` — never patch the Figma file by hand and call it done.

## Step 1 — Replay `figma-ops.json`, one op per real MCP tool call

Iterate `ops[]` in order. Each op maps to exactly one MCP tool call:

| Op | Tool call |
|---|---|
| `EnsureFile` | `mode: 'create'` → `create_new_file` in `figmaTeamPlanKey`'s team; record the returned `file_key`/`file_url`. `mode: 'mutate'` → operate inside the existing `figmaFileKey` file; never create a second one. |
| `EnsurePage` | Switch to/create the named page (`figma.setCurrentPageAsync`, never assign `figma.currentPage`). |
| `CreatePageAuditFrame` | Create a frame `widthPx × heightPx`, and set its `clipsContent` to the op's own `clipsContent` field (`false`) immediately. |
| `UploadTileBlock` | Crop `tilePath` to `[sourceCropY, sourceCropY + sourceCropHeight)` (`cropTileForBlock` in `page-composite-plan.ts` if replaying outside a live session that already has the bytes) and `upload_assets` it onto a rectangle at `(destX, destY)` sized `widthPx × sourceCropHeight`. |
| `StageComponentLibrary` | **Runs FIRST for this page, before any `CreateMarkerComponentSet` op below (Decision Log #37 — this ordering is itself part of the fix).** Create an empty Figma Section now, named `sectionLabel` from the op, at `(x, y: 0)` — **to the right of the Legend** (`x >= legend.x + legend.widthPx`), never below the frame — sized to the op's `widthPx`/`heightPx` (an INITIAL estimate only; `FinalizeComponentLibraryLayout` resizes it later from real content). Leave/set `section.visible = true` — the op's own field is the reminder. **Decision Log #34 — never hide the Section (or its members):** the three-round regression history below led to hiding as an earlier "fix," which then broke hover entirely (see the `CreateMarkerComponentSet` row below) — the actual fix is horizontal position alone. **Regression history (four rounds):** (1) an earlier version staged these at `y: totalHeightPx + 5000` — still "far away" on paper, but on the SAME vertical axis a reader scrolls down to read the report; the first time a real multi-tile page (brand-perception-survey-page) was actually scrolled, this rendered as a visible duplicate numbered findings list after the Footer — fixed by horizontal staging. (2) Horizontal staging alone still left the Section discoverable by deliberately scrolling/zooming the Figma canvas sideways — (3) hiding the Section, and every individual marker master too (**Figma Sections auto-manage membership by geometry and can silently eject an overflowing/mispositioned member as a visible top-level sibling** — the root cause behind round 5 below), was tried next and DID stop the visual leak — but (4) it also silently broke `CHANGE_TO` hover-swap for every marker in the file. The round-4 tradeoff (matching `market-entry-real-1`): stay visible, rely on horizontal distance from the Legend for isolation. **(5) Decision Log #37 — that tradeoff was necessary but not sufficient:** even fully visible, a Section built by wrapping already-created, already-positioned masters (rather than one masters are `appendChild`-ed into from the moment it exists) can still eject an overflowing/mispositioned member as a top-level sibling — observed live on the Survey file (Marker 01 and Marker 07 both ejected). Creating the Section FIRST and reparenting every master into it immediately upon creation (see the `CreateMarkerComponentSet` row) is what actually closes this. |
| `CreateMarkerComponentSet` | Build the Default/Hover variant pair from `hoverCard`'s fields verbatim (`shortName`, `status`, `severityText`, `explanation`, `bullets`, `dsLine`, `findingLabel` — do not invent or omit any). `combineAsVariants`, then **immediately** set `clipsContent = false` on the result AND leave/set `visible = true` — the op's own fields are the reminder, not a step to skip. **Decision Log #34 — do not hide this, ever:** an earlier version of this runbook instructed setting `visible = false` here, reasoning that a component's own visibility is independent of its instances' rendering and of variant-swap `CHANGE_TO` prototyping. That reasoning was live-tested and found WRONG: Figma's Presentation/Prototype-mode hover-swap silently fails to navigate to a destination variant whose component SET is hidden, even though the reaction data is completely valid and reads back fine from the Plugin API — confirmed by A/B diagnosis against the working `market-entry-real-1` reference (masters `visible: true`) vs. `brand-perception-survey-page`/`survey-page-audit`/an initial `report-store-page` build (masters `visible: false`, hover broken on every single marker in all three). Isolation from the report relies ONLY on `StageComponentLibrary`'s horizontal position now — never on hiding. **Decision Log #37 (supersedes #36's framing) — reparent into the Section IMMEDIATELY, do not just position:** the moment this master exists, `appendChild` it into the SAME page's already-created `StageComponentLibrary` Section (row above) — never leave it a top-level sibling to be "wrapped" later. Then confirm `master.parent === section` right here, before moving on to the next marker — do not defer this check to the end. Place the master at the op's `(masterX, masterY)` as an INITIAL position ONLY — this is an estimate from text content, not a live measurement, and is NOT the final position: this page's `FinalizeComponentLibraryLayout` op (after the marker-loop rows below) re-measures and re-positions every master from REAL rendered bounds. Never report a publish correct because `masterX`/`masterY` looked reasonable in `figma-ops.json` — that is exactly what shipped Marker 01/07 ejected on the Survey file. |
| `PlaceMarkerInstance` | Place the Default variant at `(x, y)` — `y` is already clamped ≥ 0, use it as given. |
| `WireHoverReaction` | `instance.reactions = [{ trigger: { type: 'ON_HOVER' }, actions: [{ type: 'NODE', destinationId: <hoverVariantId>, navigation: 'CHANGE_TO', transition: { type: 'SMART_ANIMATE', easing: { type: 'EASE_OUT' }, duration: 0.15 }, resetVideoPosition: false, resetScrollPosition: true }] }]` — match `market-entry-real-1`'s live transition values exactly (`SMART_ANIMATE` / `EASE_OUT` / `0.15`s), not `transition: null` and not an improvised duration; Figma normalizes the reaction's exact field names on write (`resetScrollPosition`/`resetVideoPosition`, not e.g. `preserveScrollPosition`) — pass them as shown here rather than guessing. |
| `FinalizeComponentLibraryLayout` | **Decision Log #37 — runs ONCE per page, after every `CreateMarkerComponentSet`/`PlaceMarkerInstance`/`WireHoverReaction` row above for that SAME page, and is the actual source of truth for final layout — never optional, never replaced by trusting the estimates above.** In order: **(1)** for every master parented under this page's Section, confirm `master.parent === section` again — reparent with `appendChild` anything Figma ejected since creation; **(2)** read each master's REAL rendered bounds via **`master.absoluteRenderBounds`, never `master.width`/`master.height`/`master.absoluteBoundingBox`** — confirmed live (all five files, 2026-09-17): a component set's own declared frame stays small (often the ~32px marker-circle size) while its Hover variant's actual card content is a child positioned to overflow that frame (`clipsContent: false` is what lets it render at all) — `width`/`height`/`absoluteBoundingBox` report only the small declared frame and will silently under-measure every card, `absoluteRenderBounds` is the one property that includes the overflowing child and gives the true visual footprint; **(3)** re-pack all of them into a single column using those real render-bounds heights, `gapPx` and `paddingPx` from the op (the same algorithm `layoutComponentLibrary` used for the initial estimate, now fed real numbers), and move each master by the delta between its current and target `absoluteRenderBounds` origin (`node.x += targetX - renderBounds.x`, same for `y`) — this works regardless of a card's left/right/below placement offset, without needing to solve each variant's internal layout by hand; **(4)** resize the Section to the union of every master's final real bounds plus `paddingPx` on every side — never a size decided in advance, and **do not move the Section's own `(x, y)` origin in this step** — its children's `x`/`y` are relative to it, so relocating the Section after they're positioned would drag them along with it; only grow `width`/`height` from the existing origin; **(5)** confirm `master.parent === section` one final time after the move/resize (a resize can itself re-trigger Figma's geometry-based membership rules). One more confirmed gotcha: `section.appendChild(master)` does **NOT** preserve a node's absolute position — it reinterprets whatever `x`/`y` the node already had as relative to the new parent, which can silently teleport it. Always reparent FIRST, then compute and apply the real positioning delta in a separate step — never assume a node stays visually put across an `appendChild`. The state after this op is what Step 2's `checkMasterParentedInLibrarySection`/`checkNoMasterOverlap`/`checkLibrarySectionContainsAllMasters` actually verify — do not run those checks before this op has run. |
| `CreateLegendPanel` | Build the panel at `(x, y)`, sized `widthPx`, with `title` (the page URL) and `colorKeyLine` verbatim at the top — unchanged from before (Decision Log #33 only changed the per-finding rows and the capture note, never the panel's own bg/border/radius/padding/URL header/color key). Then `lines` **verbatim, in order** — this IS the compact numbered list, directly under the color key, never a separate node placed elsewhere. **Per-row treatment (Decision Log #33, "richer Market Entry treatment" — do not skip either line):** each `lines[]` entry is a small vertical stack, NO colored dot/ellipse (Market Entry's own Legend has none — the colored TEXT is the only indicator): (1) `primary` as ONE Semi Bold ~12.5px text node, colored by mapping the op's own symbolic `color` (RED/ORANGE/AMBER/GRAY — same field every other op uses) to the **Legend-text hex palette** — RED `#b01f24`, ORANGE `#d97321`, AMBER `#c9992e`, GRAY `#666666` — **deliberately different from** the marker-circle/hover-card hex palette (`#e53c3c`/`#f27e21`/`#edb326`/`#8a8b92`); (2) `secondary` as a second Regular ~10.5px text node, always `#666` regardless of `color` — never colored, never merged into the primary line. This is the numbered list's ONLY home on the page — if you ever find yourself placing a second numbered list anywhere else (including "for symmetry" near the Footer), stop: that is exactly the bug `StageComponentLibrary`'s regression history above describes. **Capture note:** when `captureNote` is non-null, build ONE small bordered card below the rows — bg `#f8f6f1`, border 1px `#ebdead`, radius 6px, padding 12/10, gap 4, a bold 11px black "Capture note" title, then `captureNote`'s text verbatim as an 10.5px `#666` body (the same clean card treatment as Market Entry's own capture note) — when `captureNote` is `null`, build NOTHING here; do not invent a note, and do not keep the old bare gray text line. |
| `CreateSummaryTiles` | 00 Overview's colored stat tiles (RED/GREEN/AMBER/GRAY/BLACK per `summaryTileColor`) — never a plain table. The **`Coverage gate`** tile (B7, `figma-layout-v6`) is coloured by its VALUE, not its label: `PASSED` GREEN · `INCOMPLETE — N unaccounted` RED · `not recorded` GRAY (an audit that predates B7) — replay it exactly as planned; never recolour it by hand. |
| `CreateRootCauseCards` | 02 Root Causes — one stacked card per page-wide rule/property dedup (`buildRootCauseCards`): title, category pill, occurrence pill, explanation, affected-types/expected footer. Matches the approved reference file (market-entry-real-1) exactly — never the flat `pages['02 Global Issues']` rows. |
| `CreateComponentFindingCards` | 03 Component Findings — one evidence card per `markerGroups` entry, same numbering as the Page Audit markers: thumbnail, `cardColor` status pill (2-tone: RED=Incorrect, AMBER=everything else — see `cardStatusColor`), severity/confidence/section pills, actual→expected (with a "(N properties total)" note when truncated), recommendation, C2 finding id. |
| `CreateNeedsReviewCards` | 04 Needs Review — curated, diversity-sampled cards (`buildNeedsReviewCards`): thumbnail, amber status pill, confidence, reason, possible DS matches. Never every raw row — `shown`/`total` on the op make the curation explicit. |
| `CreateGlobalComponentCards` | 05 Global Components — Header/Footer evidence cards (thumbnail + status pill + note), now covering all four marker-eligible statuses (widened `selectGlobalComponents`), not just INCORRECT/DEVIATION. |

**Text-node gotcha (hit once building brand-perception-survey-page's card pages, now avoid it):** when creating a wrapping `TEXT` node, set `.characters` **before** `.textAutoResize = 'HEIGHT'` — setting the mode first, while the node is still empty, locks in a zero width and the node's height balloons into the thousands of pixels on layout. Append to the parent and set `layoutSizingHorizontal = 'FILL'` only after `.characters` and `.textAutoResize` are both set.

Report (don't silently drop) every entry in `coverageGaps` and `missingCompositePlanFor` — these are real, already-identified limits of what could be captured, not something to paper over.

## Step 2 — Mandatory verification (never skip, never report success without doing this)

Call `src/figma/publish-verify.ts`'s functions on what actually came back — not by eyeballing:

1. **`checkBlankImage`** per uploaded tile: `get_screenshot` it back, decode, compute `{mean, stdev}`. A near-zero stdev is the confirmed blank/gray failure mode (IMPLEMENTATION-PLAN.md §6 Spike 1) — stop and report the exact failure, do not report the publish as complete.
2. **`checkHoverCardNotClipped`** per marker: `get_screenshot` the Hover variant directly, measure its rendered height against the expected card height.
3. **`checkBounds`** for every top-level child of the page-audit frame — tiles and marker instances — **never the Legend**: the Legend is required to sit outside `frameWidthPx` by design (staged to the right of the frame), so including it here fails every time even when placement is exactly correct. The Legend's own placement is checked correctly by item 5 below (Decision Log #35 — this line previously said "and the Legend"; caught on industry-report, the first run to query a live published file for every check, where `checkLegendPlacement` passed on the same node `checkBounds` simultaneously failed).
4. **`checkMarkerTraceability`**: the placed finding ids must exactly equal `figma-plan.json`'s `pageAudits[i].markerGroups` ids — no invented, dropped, or renumbered markers.
5. **`checkLegendPlacement`**: the Legend sits to the right of the frame, and no stray list content exists anywhere else (e.g. after the Footer).
6. **`checkNoMatchMarkers`**: every placed marker color is RED/ORANGE/AMBER/GRAY — never a MATCH-colored marker.
7. **`checkComponentLibraryVisible`**: the marker-master/component-library Section AND every individual marker master must have `visible: true` (Decision Log #34 — inverted from the old, disproven `checkComponentLibraryHidden`; hiding any of these breaks hover, see the `CreateMarkerComponentSet`/`StageComponentLibrary` rows above). **This alone is NOT enough to confirm correct containment** — a master can be fully visible and still have been ejected as a top-level sibling, or still overlap a neighbor; items 9-11 below are what actually catch that.
8. **Live hover-integrity checks (Decision Log #34 — mandatory, query the PUBLISHED file, never rely on `figma-ops.json` alone for these):** for every placed marker instance, `use_figma` to read back `instance.reactions`, `await instance.getMainComponentAsync()`, and walk the destination's ancestor chain, then call:
   - **`checkMarkerHasHoverReaction`** — fails if a marker instance has zero reactions, or has reactions but none is `ON_HOVER`.
   - **`checkHoverTargetResolvable`** — fails if the reaction's `destinationId` doesn't resolve to a real node, OR that node exists but is `visible: false`, OR any ancestor up to the page (its component set, any wrapping Section) is `visible: false`. A node ID that merely *exists* is not "resolvable" in the sense that matters — Presentation mode still won't navigate to it if hidden.
   - **`checkMarkerComponentSetValid`** — fails if `instance.getMainComponentAsync()` returns null (detached/missing component), or if that component's parent is not a `COMPONENT_SET` (no Default/Hover pair to swap between).
   - **`checkMarkerReactionCountMatches`** — fails if the number of placed marker instances doesn't exactly equal the number carrying a valid `ON_HOVER` reaction (catches a marker silently placed without ever being wired, even when `checkMarkerTraceability` — which only checks finding ids — passes).
   Pass all of this into `buildVerificationReport`'s `liveMarkerHoverRecords` input (or call `buildLiveHoverVerificationReport` directly) — never skip it because `figma-ops.json` already "looks right" on paper; that is exactly what looked right on all three broken files before this diagnosis.
9. **Live component-library containment checks (Decision Log #37 — mandatory, run only AFTER `FinalizeComponentLibraryLayout` has executed for this page, never against `figma-ops.json`'s initial `masterX`/`masterY` estimate alone):** for the page's Section and every master inside it, `use_figma` to read back `node.parent?.id` and each master's real `x`/`y`/`width`/`height`, then call:
   - **`checkMasterParentedInLibrarySection`** — fails if ANY master's live `parent.id` is not the Section's id, i.e. it was ejected as a top-level sibling. This is the DIRECT structural check for the exact bug reported live on the Survey file (Marker 01 and Marker 07 ejected) — a purely geometric/visibility check (item 7 above) can pass while this one fails.
   - **`checkNoMasterOverlap`** — fails if any two masters' REAL rendered rectangles overlap.
   - **`checkLibrarySectionContainsAllMasters`** — fails if any master's real bounds extend outside the Section's own real bounds (the Section was never actually resized to fit).
   Pass all of this into `buildVerificationReport`'s `componentLibrary` input (`{ sectionId, sectionBounds, masters }`) — never omit it, and never substitute the plan's initial estimate for a live read. **A publish with any of these three failing is NOT complete** — go back to `FinalizeComponentLibraryLayout`'s procedure (reparent → re-measure → re-pack → resize → re-verify) rather than reporting success with a known containment failure.

Write the aggregated result (`buildVerificationReport`, one call per page) to `figma-verification.json` alongside the run's other outputs.

## Step 3 — Report back

Exactly the fields the operator needs: Figma file URL, pages/sections created, marker count per page, root-cause group count, the Step 2 PASS/FAIL table (with the pixel-variance/bounds/traceability evidence, not just "looked fine"), and any `coverageGaps`/`missingCompositePlanFor` entries. If Step 2 finds a real problem, report it plainly — never silently patch over a failure by calling it done anyway. Then write the real `figmaFileKey`/`figmaFileUrl` back into `project.json`.

## Known, still-open limitations (be upfront about these, don't paper over them)

- The headless Claude Code publish path (`src/figma/publish.ts`, `prompt-contract.ts`'s `buildPublishInstruction`) remains genuinely blocked on Figma auth (IMPLEMENTATION-PLAN.md §6, Spike 3) — LEGACY, do not extend, this runbook does not fix that, it's a different path entirely (text-instruction, no image upload, no interactive components).
- `page-composite-plan.ts`'s header-height detection (`detectRepeatedBandHeight`) is tuned against one real page's contrast profile (`highDiffThreshold: 150`). A page with a much lower-contrast header/content boundary could need a different threshold — if the detected height looks wrong (e.g. 0 on a page you can see has a sticky header, or absurdly large), pass an explicit override rather than trusting a bad auto-detection blindly, then regenerate with `pnpm run agent figma-plan <runId>`.
- There is still no CLI `publish` command (OUT-4, a deliberate scope decision, not an oversight) — Figma's write API needs a live, authenticated interactive session; a headless process cannot do it (confirmed, not a choice). This runbook is the supported path to an actual Figma write.
- **Decision Log #37 is now live-proven, not just unit-tested (confirmed 2026-09-17):** all five files (Market Entry, Brand Perception, Survey, Report Store, Industry Report) were repaired live via `figma-plan <runId>` regeneration + a live Figma-MCP session, and Step 2's items 9-11 (`checkMasterParentedInLibrarySection`/`checkNoMasterOverlap`/`checkLibrarySectionContainsAllMasters`) plus live hover-integrity checks passed on all five (see each run's `figma-verification.json`). Confirmed live findings that went beyond the originally-reported bug: Market Entry had no Section at all (never wrapped, predates the concept entirely); Industry Report's masters were correctly parented but the Section was never resized/repositioned to actually contain them (real overlap + horizontal escape); Brand Perception had 8 of 12 masters ejected (already flagged `⚠` by an earlier session) — most severe of the five; Survey had exactly the reported ejections (Marker 01/07) plus a separate bug: 5 masters had `clipsContent: true`, meaning their hover cards were completely invisible even before considering ejection; Report Store had a minor 8px top-edge escape. All fixed and re-verified live, including screenshots.
